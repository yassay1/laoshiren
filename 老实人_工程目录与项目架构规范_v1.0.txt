《老实人｜工程目录与项目架构规范 v1.0》

版本：v1.0
项目名称：老实人
文档类型：Repository / Project Architecture Specification
当前阶段：正式开发前最终工程结构定版
目标：
1. 最大程度实现“老实人”Agent 产品能力；
2. 服务于 2026 鸿蒙应用开发者激励计划；
3. 建立成熟、工程化、可维护、可扩展的 Agent 项目结构。

==================================================
1. 总体架构结论
==================================================

老实人采用：

Monorepo
+
HarmonyOS Native Client
+
Modular Monolith Backend
+
Clean Architecture
+
DDD-lite
+
Agent Orchestration

核心原则：

1. HarmonyOS 客户端使用 ArkTS + ArkUI 原生开发；
2. FastAPI 后端保持一个主部署单元，不做无必要微服务；
3. 普通业务后端先成立，Agent 不是业务能力本身；
4. Application + Domain 构成业务系统核心；
5. Executive Agent 通过 Tool 调用 Application Use Case；
6. UI、Agent、Worker 最终共享同一套 Application / Domain；
7. Infrastructure 负责技术实现细节；
8. LangGraph 只负责 Agent Runtime / Orchestration；
9. 数据库、LLM、Search、Push 等不得反向污染 Domain；
10. 架构保持成熟边界，但 Python 实现保持轻量，避免过度抽象。

最终调用关系：

普通结构化操作：

HarmonyOS
    ↓
Presentation API
    ↓
Application
    ↓
Domain
    ↓
Infrastructure


自然语言操作：

HarmonyOS Chat
    ↓
FastAPI Run API
    ↓
Executive Agent
    ↓
Tool
    ↓
Application
    ↓
Domain
    ↓
Infrastructure


后台任务：

Worker
    ↓
Application
    ↓
Domain
    ↓
Infrastructure

7. Presentation Layer
==================================================

位置：

presentation/api/


职责：

- HTTP Request / Response；
- FastAPI Router；
- Authentication / Dependency；
- Pydantic Validation；
- SSE / Streaming；
- HTTP Error Mapping；
- API Versioning。


禁止：

- 核心业务规则；
- SQL；
- Agent 推理；
- LLM 调用；
- 业务状态直接修改。


API Schema 位于：

presentation/api/schemas/


Schema 表示：

HTTP Contract

例如：

CreateThingRequest
UpdateThingRequest
ThingResponse
RunRequest
RunResponse


API Schema 不等于 Domain Entity。


==================================================
8. Application Layer
==================================================

Application 表示：

“老实人可以执行哪些业务用例。”


它是此前讨论的“原子能力”的正式工程实现层。


例如：

PersonalStateApplicationService

create_thing()
update_thing()
create_task()
complete_task()
reopen_task()
set_deadline()
add_blocker()
attach_source()


Application 负责：

- Use Case orchestration；
- Repository / Port 调用；
- Transaction boundary；
- 调用 Domain 行为；
- 组织多个 Domain 对象；
- 返回 Application DTO；
- 触发必要 Domain Event / Application Event。


Application 不负责：

- FastAPI；
- UI；
- LangGraph routing；
- SQLAlchemy ORM 细节；
- LLM provider 细节。

Domain 原则：

不得依赖：

FastAPI
LangGraph

10. Infrastructure Layer
==================================================

Infrastructure 保留。

原因：

老实人拥有大量可替换的技术实现：

- PostgreSQL；
- pgvector；
- LangGraph Checkpoint Store；
- LLM；
- Embedding；
- Object Storage；
- Web Search；
- Push；
- Calendar；
- Speech；
- Document Processing；
- Job Runtime。


Infrastructure 只负责：

“这些抽象能力具体怎么实现。”


例如：

Application Port：

TaskRepository


Infrastructure：

PostgresTaskRepository


Application Port：

ObjectStorage


Infrastructure：

OBSObjectStorage
或
MinIOObjectStorage


Application Port：

SearchProvider


Infrastructure：

WebSearchAdapter


核心依赖：

Application / Domain
定义抽象

Infrastructure
实现抽象。

23. AI Coding Agent 项目规范
==================================================

根目录保留：

主要写：

- 架构边界；
- 依赖方向；
- 禁止事项；
- 测试要求；
- Tool 规则；
- Personal State / Memory 边界。


示例：

- Domain must not import FastAPI or LangGraph.
- Agent tools must call Application services.
- LLM must never execute SQL directly.
- Personal State is the current operational truth.
- Memory must not override current Personal State.
- External side effects require idempotency.
- Do not create a new Agent unless independent multi-step autonomy is required.
- HarmonyOS client must not contain provider secrets.

24. Monorepo 原则
==================================================

当前使用单 Git Repository。


原因：

一个功能通常跨越：

ArkTS
FastAPI API
Application
Agent Tool
DB
Contract


Monorepo 可以：

- 一次 Commit 完成完整 Feature；
- 同步管理接口；
- 统一 CI；
- 统一 Docs；
- 统一版本；
- 降低一个人开发维护成本。


V1 不拆：

backend repo
client repo
agent repo

26. 架构成功标准
==================================================

如果未来：

更换 LLM

应该主要改：

infrastructure/llm/


更换 PostgreSQL implementation

应该主要改：

infrastructure/persistence/


更换 Agent Runtime

应该主要改：

agent/


增加新的 HarmonyOS 页面

应该主要改：

apps/harmonyos/features/


修改：

“Deadline 如何验证”

应该主要改：

domain / application


增加：

新的 Agent Tool

应该主要：

agent/tools
+
reuse existing Application


如果一个普通业务改动需要：

同时修改 Agent Graph、Router、ORM、UI、大量 unrelated module

说明架构边界出现问题。

27. 官方与成熟项目参考原则
==================================================

本架构主要吸收以下成熟方向：

HarmonyOS 官方：
- ArkTS / ArkUI 原生应用开发；
- 分层架构；
- 高内聚低耦合；
- Feature 模块化；
- MVVM；
- 原生 Kit 能力。

FastAPI 官方：
- Bigger Applications；
- APIRouter；
- Pydantic Request / Response；
- OpenAPI；
- 多文件 Package。

Python Packaging：
- src layout；
- pyproject.toml。

uv：
- uv.lock；
- reproducible dependencies。

Clean Architecture / DDD：
- Domain 中心；
- Application Use Case；
- Infrastructure Adapter；
- Dependency Inversion。

LangGraph：
- Agent runtime 与业务系统解耦；
- State / Tool / Graph；
- Durable Execution；
- Interrupt / Resume；
- Subgraph。

OpenHands：
- Agent、Tool、Runtime / Workspace / Server 之间的明确边界；
- Agent 不等于整个应用。

Dify：
- Controller / Service / Domain / Worker 分工；
- 异步副作用幂等；
- Agent/Workflow 构建在稳定后端能力之上。

28. 最终架构一句话
==================================================

老实人首先是一套完整、可靠、可被普通客户端直接使用的个人事务后端系统。

Application + Domain 提供稳定业务能力。

Infrastructure 提供数据库、模型、搜索、存储、Push 等技术实现。

HarmonyOS UI、Executive Agent 和 Background Worker 都作为不同入口复用同一套业务能力。

Executive Agent 的价值不是替代后端，而是在这些稳定能力之上，通过 Context、Tool Calling、自主规划、并行执行和长期记忆形成智能编排。

这构成老实人的最终工程架构基线。
