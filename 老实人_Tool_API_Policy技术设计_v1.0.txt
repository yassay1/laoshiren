《老实人｜Tool / API / Policy 技术设计 v1.0》

版本：v1.0
项目名称：老实人
文档类型：Tool / API / Policy Technical Design
当前阶段：V1 正式开发设计
后端：Python + FastAPI
Agent Runtime：LangGraph
目标：定义 Executive Agent 可调用的 Tool、FastAPI 对客户端暴露的接口、Tool Policy、HITL、幂等、错误模型与流式事件规范

==================================================
0. 文档目的
==================================================

本文件用于把老实人 V1 的“执行层”正式固定下来。

它重点回答：

1. Executive Agent 可以调用哪些 Tool；
2. Tool 如何命名、分组、返回结果；
3. Tool 是否直接操作数据库；
4. 哪些操作可以自动执行，哪些必须用户确认；
5. FastAPI 如何承接 HarmonyOS 客户端；
6. Chat / Run / Thread / Source / Thing / Automation API 如何设计；
7. SSE 如何传输 Agent 流式结果；
8. interrupt / resume 如何穿过 API 到达客户端；
9. Tool 失败、冲突、重试如何统一表达；
10. 如何避免重复创建提醒、日历事件或重复更新状态；
11. 如何保留 Trace、Run 和 ToolExecution 记录。

核心原则：

Agent 负责“决定做什么”。

Tool 负责“把动作标准化”。

Domain Service 负责“按照业务规则真正执行”。

Database / External API 负责“保存或产生真实世界结果”。

正确层级：

Executive Agent
      ↓
Tool
      ↓
Policy
      ↓
Domain Service
      ↓
Database / External API
      ↓
Tool Result
      ↓
Executive Agent


==================================================
1. Tool 不是业务数据库接口
==================================================

错误设计：

Executive Agent
→ update_sql(...)
→ PostgreSQL


不推荐原因：

- LLM 不应直接理解数据库 schema；
- SQL 参数难以安全约束；
- 业务规则无法统一；
- 并发控制容易遗漏；
- 幂等难实现；
- 后续数据库重构会影响 Agent Tool；
- Tool Schema 对模型不友好。


正确设计：

Executive Agent
→ state.update_task(...)
→ Policy
→ PersonalStateService
→ Repository / Transaction
→ PostgreSQL


Tool 是“面向 Agent 的领域能力”。

Service 是“面向代码的业务能力”。

Repository 是“面向数据库的数据能力”。

2. Tool 总体分类
==================================================

V1 Tool Namespace：

state.*
memory.*
source.*
document.*
image.*
audio.*
search.*
automation.*
notification.*
calendar.*
system.*


建议：

读取能力和写入能力尽量从名字上可辨别。

例如：

state.get_thing
state.search_things
state.update_task

而不要：

state.execute
state.process


Tool 名称必须：

- 语义明确；
- 单一职责；
- 参数稳定；
- 对模型友好；
- 不暴露底层实现。


==================================================
3. Tool Registry
==================================================

建议建立统一 Tool Registry。

Tool Registry 负责：

- Tool 注册；
- Tool 描述；
- JSON / Pydantic Schema；
- Tool category；
- risk level；
- timeout；
- retry policy；
- approval policy；
- execution handler；
- observability metadata。


概念结构：

ToolDefinition
├── name
├── description
├── input_schema
├── category
├── risk_level
├── timeout_seconds
├── retry_policy
├── requires_confirmation
├── idempotent
├── handler
└── enabled


Executive Agent 不直接 import 所有 Service。

而是通过 Tool Registry 获取当前可用能力。


==================================================
4. 动态 Tool 暴露
==================================================

随着 Tool 增多，不应每轮把所有 Tool Schema 全部发送给模型。

V1 Tool 数量较少时：

可以直接加载主要 Tool。

后续可根据：

- current input；
- Thing type；
- Skill；
- current stage；

动态选择 Tool Set。


例如：

用户讨论 PDF：

优先暴露：

document.interpret
source.get
state.*
search.*


不需要暴露：

calendar.update
notification.push
automation.cancel


目标：

减少 Context 占用
+
降低 Tool Selection 错误。


==================================================
5. Tool 通用输入字段
==================================================

所有 Mutation Tool 不必把运行字段暴露给模型。

例如：

run_id
action_id
user_id
idempotency_key

应由 Runtime 自动注入。


模型只提供业务参数：

state.update_task(
  task_id,
  status,
  reason
)


Runtime 自动补：

user_id
run_id
action_id
idempotency_key


这样可以减少：

- 参数错误；
- 越权；
- Tool Prompt 冗余。


==================================================
6. Tool Result 统一结构
==================================================

建议所有 Tool 最终转化为统一结果：

ToolResult
├── status
├── code
├── message
├── data
├── error
├── source_refs
├── mutation_refs
├── retryable
├── requires_user_input
└── metadata


status：

SUCCESS
PARTIAL
FAILED
NOT_FOUND
CONFLICT
REQUIRES_CONFIRMATION
REQUIRES_USER_INPUT


code 示例：

THING_NOT_FOUND
TASK_NOT_FOUND
AMBIGUOUS_THING
VERSION_CONFLICT
EXTERNAL_TIMEOUT
INVALID_ARGUMENT
PERMISSION_DENIED
DUPLICATE_ACTION
UNSUPPORTED_FILE
RATE_LIMITED


ToolResult.message：

用于 Agent 理解执行结果。

不是必须直接展示给用户。


==================================================
7. Tool Error 不抛给最终用户
==================================================

Service 可以抛内部异常。

Tool Adapter 应转成标准 ToolResult。

例如：

ExternalCalendarTimeout
↓
Tool Adapter
↓
ToolResult(
 status=FAILED,
 code=EXTERNAL_TIMEOUT,
 retryable=true
)


Executive Agent：

根据 Tool Result 决定：

- 自动重试；
- 换方案；
- 告知用户；
- 暂停等待；
- 放弃。


用户不应该看到：

Python traceback
SQL error
SDK internal error

==================================================
17. Tool Risk Level
==================================================

建议四级：

READ
LOW_WRITE
SENSITIVE_WRITE
IRREVERSIBLE


READ：

- state.get_*
- memory.search
- source.get
- search.*
- document.interpret


LOW_WRITE：

- state.update_task
- state.create_task
- automation.create
- source.attach_to_thing


SENSITIVE_WRITE：

- calendar.create/update
- notification.push
- memory.forget
- important deadline overwrite


IRREVERSIBLE：

- physical delete
- external send to third party
- payment
- irreversible submission


V1 可以先不实现高风险工具，
但 Policy 模型从第一天保留。


==================================================
18. Policy Layer
==================================================

Policy 不只是一段 System Prompt。

正确：

Prompt Rules
+
Deterministic Policy Code
+
Domain Validation
+
Human Confirmation


四层分工：

Prompt
→ 告诉 Agent 应遵守什么规则。

Tool Policy
→ 代码决定当前调用是否允许。

Domain Service
→ 业务规则验证。

HITL
→ 人确认高风险行为。


模型不能通过“自己认为安全”绕过 Policy。


==================================================
19. Policy Decision
==================================================

PolicyResult：

ALLOW
DENY
REQUIRE_CONFIRMATION
REQUIRE_MORE_CONTEXT


附带：

reason
confirmation_payload
policy_code


例：

calendar.delete(event_id)

如果：

event.owner != agent
且用户没有明确要求删除

Policy：

REQUIRE_CONFIRMATION


==================================================
20. 用户明确意图与确认
==================================================

不要所有写操作都弹确认。

否则产品会非常烦。


原则：

明确用户指令
+
低风险
+
可逆
→ 可直接执行


例：

“把Demo标记完成。”

→ 直接 state.update_task


模糊推断
+
可能影响关键事实
→ Verify / Ask


例：

“老师好像延期了。”

→ 不直接修改 verified deadline


高风险
→ Confirm

==================================================

  "interrupt_id": "...",

  }
}


Backend：

Command(resume=...)


Graph 从 checkpoint 恢复。

22. FastAPI API 总体原则
==================================================

客户端 API 和 Agent Tool API 是两套概念。


HarmonyOS Client
→ FastAPI Public API


Executive Agent
→ Internal Tool Runtime


客户端不能直接调用：

/tool/state.update_task


客户端应调用：

/things
/threads
/runs
/sources
/automations


原因：

客户端 API 是产品接口。

Tool 是 Agent 内部能力。

25. Run API
==================================================

核心入口：

POST /api/v1/runs


Request：

{
  "thread_id": "...",
  "message": {
    "type": "text",
    "content": "Demo做完了"
  },
  "source_ids": []
}


Response：

202 Accepted

{
  "run_id": "...",
  "thread_id": "...",
  "status": "queued_or_running",
  "stream_url": "/api/v1/runs/{run_id}/events"
}


为什么不要求 HTTP 请求一直等 Agent 完成：

复杂 Agent Run 可能：

- 多次 Tool；
- 搜索；
- 并行；
- interrupt；
- 用户退出 App。


Run 应作为独立资源。

==================================================
45. Retry Policy
==================================================

Tool 不是所有错误都重试。


可重试：

- timeout；
- temporary network；
- 429；
- 503；
- transient DB connection。


不可直接重试：

- invalid argument；
- permission denied；
- version conflict；
- user confirmation required；
- not found（大部分情况下）。


指数退避：

可在 Tool Runtime 实现。

46. Timeout
==================================================

每个 Tool 定义 timeout。


示意：

3-5s

DB mutation：
5s

web search：
10-20s

document interpretation：
更长

Specialist Agent：
Run-level timeout


不要让一次外部 Tool 无限挂起整个 Agent。

47. Background Tasks
==================================================

FastAPI BackgroundTasks 适合：

- 小型后处理；
- 轻量通知；
- 写日志等。


但老实人的：

- Memory Formation；
- Heavy Document Processing；
- Automation condition watch；
- 长时间 Agent job；

不应依赖单进程 BackgroundTasks 作为最终生产方案。


V1 初期开发：

可以先简化。


一旦任务需要：

跨进程
持久执行
重试
定时
失败恢复

应使用独立 Worker / Job Queue / Scheduler。

82. 当前设计结论
==================================================

老实人的执行接口层最终遵循：

Client API
≠
Agent Tool


HarmonyOS Client
通过 FastAPI Product API 使用产品。

Executive Agent
通过 Internal Tool Runtime 操作系统。


所有真实写操作：

Tool
→ Policy
→ Domain Service
→ Persistence / External API


所有 Tool：

统一 Result
统一 Trace
统一错误模型
统一幂等策略


所有高风险动作：

不能只依赖 Prompt，
必须有代码级 Policy / Approval。


Run：

是独立、可持久、可恢复的执行资源。

SSE：

只是客户端观察 Run 的流式通道，
不是 Run 生命周期本身。


最终形成：

     ↓

     ↓

     ↓

     ↓

     ↓

     ↓
