《老实人｜产品需求文档 PRD v1.0》

版本：v1.0
项目名称：老实人
文档类型：Product Requirements Document
当前阶段：V1 产品定义 / 正式开发准备
目标平台：HarmonyOS
产品形态：个人事务智能体应用


==================================================
1. 文档目的
==================================================

本 PRD 用于定义“老实人”V1 的产品目标、核心用户流程、功能模块、关键产品行为和验收标准。

本文件重点回答：

- 用户为什么使用老实人；
- 用户如何与老实人交互；
- 系统需要管理哪些现实事务；
- Agent 在什么情况下应该回答、执行、提醒或追问；
- 多模态内容进入系统后应该发生什么；
- V1 做到什么程度才算真正成立。

本文件暂不详细定义：

- 数据库表结构；
- LangGraph 具体节点；
- API 字段；
- Tool Function Schema；
- ArkUI 具体页面视觉稿；
- 最终 UI 设计语言。

这些内容在后续技术设计文档中继续确定。


==================================================
2. V1 产品目标
==================================================

老实人 V1 的目标不是做一个只能演示几轮对话的 Agent Demo。

V1 应当成为一个可以真实安装、真实持续使用、能够维护用户现实事务的 HarmonyOS 应用。

V1 需要完成以下核心闭环：

现实世界发生变化
      ↓
用户通过文字 / 文件 / 图片 / 语音 / 分享告诉老实人
      ↓
Agent 理解发生了什么
      ↓
识别相关 Thing / 当前上下文
      ↓
获取必要 Personal State / Memory / Source
      ↓
判断是否需要执行行动
      ↓
Tool / State Update / Search / Automation / Calendar 等
      ↓
形成新的当前状态
      ↓
后续持续追踪
      ↓
必要时主动提醒或 Push


V1 重点不是“功能数量最多”，而是核心能力形成真实闭环：

1. 能持续理解用户正在推进的事情；
2. 能准确维护事务的当前状态；
3. 能跨对话继续长期事项；
4. 能理解多模态现实输入；
5. 能真正调用工具推进事情；
6. 能在合适时机主动提醒；
7. 用户未打开 App 时可以通过 Automation + Push 继续触达；
8. App 本身具有完整、统一、可长期使用的产品体验。


==================================================
3. 用户与使用场景
==================================================

老实人面向存在以下需求的个人用户：

- 同时处理多个项目或任务；
- 需要长期跟进不同事情；
- 经常收到截图、通知、PDF、Word、PPT 等资料；
- 容易忘记当前进度或截止时间；
- 需要记录“事情现在做到哪里”；
- 需要重新进入某个长期事项；
- 希望系统能主动发现值得关注的问题；
- 希望部分事情可以由 Agent 直接执行。

典型事务包括：

- 比赛；
- 学习；
- 课程；
- 论文；
- 项目；
- 工作；
- 实习；
- 申请；
- 活动；
- 日常计划；
- 个人长期目标；
- 其他需要持续维护的现实事务。


==================================================
4. 产品核心对象：Thing
==================================================

Thing 是老实人中表示“一个持续存在的现实事务”的核心对象。

Thing 不是单纯 Todo。

一个 Thing 可以包含：

- 多个阶段；
- 多个 Task；
- 多个 Deadline；
- 多份 Source；
- 多次状态变化；
- 多个相关人员；
- 多个未来行动；
- 一段持续数天、数周甚至数月的历史。


--------------------------------------------------
4.1 Thing 示例
--------------------------------------------------

示例 A：

Thing：
“AI杭州智能体比赛”

可能包含：

status = BUILDING
current_stage = 开发阶段
deadline = 2026-09-19

tasks：
- Demo
- 技术报告
- 演示视频
- 提交材料

sources：
- 官方通知 PDF
- 群聊截图
- 报名页面
- 老师要求

next_actions：
- 完成 Demo
- 整理技术文档


示例 B：

Thing：
“论文投稿”

可能包含：

current_stage = 修改
status = ACTIVE

tasks：
- 修改摘要
- 检查公式
- 调整参考文献
- 投稿

related_people：
- 指导老师
- 团队成员


--------------------------------------------------
4.2 Thing 建议字段
--------------------------------------------------

Thing V1 建议从以下维度表达：

【身份】
- 名称
- 类型
- 简要描述

【当前状态】
- status
- current_stage
- progress
- priority

【时间】
- start time
- deadline
- important dates

【任务】
- tasks
- completed items
- pending items

【下一步】
- next actions

【问题】
- blockers
- risks

【关系】
- related people
- related things

【资料】
- related sources

【变化】
- recent updates
- last updated


原则：

不要因为“越详细越好”就无限增加字段。

字段是否进入 Personal State，应满足至少一个条件：

1. 会影响 Agent 当前判断；
2. 用户未来很可能询问；
3. 会影响下一步行动；
4. 会影响提醒；
5. 会影响 Tool 执行；
6. 能表达事务真实状态。

如果只是一次性的聊天内容，没有长期价值，不应强制进入 Thing。


==================================================
5. 核心功能模块
==================================================

V1 从产品角度划分为以下能力模块：

1. Chat
2. Things
3. Today / Attention
4. Timeline
5. Sources / Multimodal Input
6. Memory
7. Tool Execution
8. Automation
9. Notification / Push
10. Search
11. Settings


==================================================
6. Chat
==================================================

Chat 是用户与 Executive Agent 的主要交互入口。

用户可以：

- 自然聊天；
- 汇报事务变化；
- 提问题；
- 分享资料；
- 要求执行操作；
- 查询某个 Thing；
- 创建提醒；
- 继续过去的事情；
- 发起复杂任务。


--------------------------------------------------
6.1 自然输入
--------------------------------------------------

用户不需要学习固定命令。

例如：

“Demo做完了。”

“老师刚刚又改要求了。”

“帮我看看这个PDF。”

“之前那个比赛最后怎么定的？”

“明天下午提醒我交报告。”

“这个项目现在还有什么没做？”

“帮我把这三个比赛都查一下，看我最适合参加哪个。”


系统应根据上下文自主判断：

- 这是普通对话；
- 这是状态变化；
- 这是事实信息；
- 这是用户计划；
- 这是 Tool Request；
- 这是需要搜索的问题；
- 这是需要 Memory 的问题；
- 这是需要追问的问题；
- 这是一个复杂任务。


--------------------------------------------------
6.2 流式响应
--------------------------------------------------

Agent 回复应支持流式展示。

当后台需要调用 Tool 时，客户端可以适度展示状态，例如：

- 正在查看资料；
- 正在查询最新信息；
- 正在检查当前进度；
- 正在更新事务；
- 正在处理文件。

不应把低层工具日志、内部 Prompt、Chain-of-Thought 或复杂执行细节直接暴露给用户。


==================================================
7. Things
==================================================

Things 用于让用户直接查看当前现实事务。

用户不应只能通过聊天才能知道系统记住了什么。

Things 需要提供：

- 当前所有主要事务；
- 状态；
- 优先级；
- 截止时间；
- 当前阶段；
- 当前进度；
- 重要任务；
- 下一步行动。


--------------------------------------------------
7.1 Thing Detail
--------------------------------------------------

进入某个 Thing 后，用户应能看到：

1. 当前状态
2. 当前阶段
3. Deadline / Important Dates
4. Tasks
5. Next Actions
6. Blockers
7. Related Sources
8. Related People
9. Recent Changes
10. Timeline


用户可以：

- 查看；
- 手动修改；
- 通过 Chat 修改；
- 查看状态变化历史；
- 进入相关 Source；
- 继续和 Agent 讨论该 Thing。


--------------------------------------------------
7.2 Thing 创建
--------------------------------------------------

Thing 可以通过两种主要方式创建：

A. 用户明确创建

例如：

“新建一个事情，叫鸿蒙应用开发。”

B. Agent 识别后建议 / 自动创建

例如用户连续讨论一个新的长期项目。

Agent 判断这已经是一个持续事务时，可以：

- 直接创建（低风险情况下）；
- 或询问用户是否创建；
- 或先作为临时上下文存在。

具体自动创建策略后续在 Policy 文档确定。


==================================================
8. Today / Attention
==================================================

Today 用于展示“今天最值得关注什么”。

它不是普通 Todo List，而是 Personal State + Attention 的产品入口。

Today 可以包含：

- 今日截止事项；
- 已逾期事项；
- 即将截止的重要事项；
- 高优先级事项；
- 长时间阻塞事项；
- 长时间无进展但重要的 Thing；
- 系统认为值得关注的 Next Action。


--------------------------------------------------
8.1 聊天中的主动提醒
--------------------------------------------------

当用户正在 Chat 时，Agent 可以获取少量 Attention Candidates。

例如：

用户：
“今天食堂太难吃了。”

系统发现：
“技术报告今天截止，目前 TODO。”

Agent 可以正常响应当前话题，并在合适时补充：

“对了，你今天还有技术报告截止，现在还没记录完成。”


主动提醒原则：

1. 当前事项确实重要；
2. 与时间敏感度相关；
3. 不频繁重复；
4. 不因为所有小任务打断用户；
5. 用户明确忽略后进入冷却；
6. 用户当前正在处理更重要的事情时，可以暂不插入；
7. Agent 决定表达方式，不使用机械固定模板。


--------------------------------------------------
8.2 Attention 候选
--------------------------------------------------

V1 至少支持：

- overdue
- due_today
- due_soon
- high_priority
- blocked_too_long
- inactive_important_thing


==================================================
9. Timeline
==================================================

Timeline 记录用户现实事务的重要变化。

例如：

08/20
比赛正式报名

08/21
Demo 完成

08/22
老师要求增加技术报告

08/23
官方截止时间变更


Timeline 不是完整聊天记录。

只记录有现实意义的 Event，例如：

- 状态变化；
- Deadline 变化；
- Task 创建 / 完成；
- 重要决定；
- Source 加入；
- Tool 执行；
- Automation 创建；
- 关键外部变化。


Timeline 的价值：

- 用户可以快速回顾发生过什么；
- Agent 可以理解事情发展过程；
- 为后续 Episodic Memory 提供来源；
- 用户可以发现错误更新。


==================================================
10. Sources 与多模态输入
==================================================

用户现实中的信息大量来自文件和其他 App。

V1 支持：

- 文字；
- 图片；
- 截图；
- PDF；
- Word；
- PPT；
- 语音；
- 其他 App 分享。


--------------------------------------------------
10.1 Source 原则
--------------------------------------------------

原始输入尽可能保留为 Source。

Source 至少记录：

- 类型；
- 原始文件 / 内容；
- 时间；
- 来源；
- 所属用户；
- 可选的 related Thing；
- 基础元数据。


系统不应只保存“AI总结结果”而丢掉原始来源。


--------------------------------------------------
10.2 图片 / 截图
--------------------------------------------------

典型场景：

用户分享比赛群通知截图。

系统可能执行：

图片理解
→ 提取通知内容
→ 判断关联 Thing
→ 识别 Deadline / Requirement
→ 对照当前状态
→ Agent 判断是否需要修改
→ 更新 / 询问 / 搜索验证


--------------------------------------------------
10.3 PDF / Word / PPT
--------------------------------------------------

用户分享文档后，Agent 应根据用户需求决定：

- 总结；
- 搜索特定内容；
- 提取任务；
- 提取要求；
- 提取 Deadline；
- 判断是否影响当前 Thing；
- 创建 Task；
- 更新状态；
- 作为长期 Source 保存。


不能固定成：

“上传文件 → 自动总结”。

文档理解服务于当前 Agent 任务。


--------------------------------------------------
10.4 语音
--------------------------------------------------

V1 语音输入至少支持：

语音
→ 转写
→ Agent Context

后续可扩展：

- 保留原始音频；
- 说话人区分；
- 会议纪要；
- 自动抽取事务变化。


--------------------------------------------------
10.5 其他 App 分享
--------------------------------------------------

用户在其他 App 中看到：

- 网页；
- 图片；
- 文档；
- 通知；
- 其他可分享内容；

可以通过系统分享能力发送到老实人。

老实人接收后创建 Source/Event。

用户可以附带一句话：

“这个是比赛新通知。”

“帮我记一下。”

“看看有没有改截止时间。”

“这个跟我的论文有关。”


==================================================
11. 跨对话继续
==================================================

每个 Chat Thread 可以保持相对独立。

用户可以新建干净对话，而不必带入全部旧聊天历史。

但系统仍然可以通过：

- Personal State；
- Long-term Memory；
- Source；
- Thing；

恢复与当前问题相关的历史背景。


例如：

Thread A：

用户讨论“鸿蒙激励计划”。

数天后开启 Thread B：

“之前那个鸿蒙应用，我们最后定的技术栈是什么？”

系统应能找到相关长期记忆或 Thing，而不是要求用户重新解释。


==================================================
12. Memory 产品行为
==================================================

Memory 在产品层面应表现为：

“系统能够记住真正长期有价值的信息。”

而不是：

“所有聊天内容永久保存并全部注入模型。”


--------------------------------------------------
12.1 Profile Memory
--------------------------------------------------

用于稳定用户信息和偏好，例如：

- 偏好的提醒方式；
- 常用工作习惯；
- 交互偏好；
- 长期目标。


--------------------------------------------------
12.2 Semantic Memory
--------------------------------------------------

用于长期事实与决定，例如：

- 某项目最终采用的架构；
- 某次讨论已经确定的技术路线；
- 某个重要要求；
- 用户和某件事情之间的长期关系。


--------------------------------------------------
12.3 Episodic Memory
--------------------------------------------------

用于过去经验，例如：

- 上一次类似项目采用了什么方法；
- 某次任务哪里出了问题；
- 某个方案最后效果如何。


--------------------------------------------------
12.4 Memory 与 Personal State 边界
--------------------------------------------------

如果信息描述“当前情况”，优先进入 Personal State。

例如：

“技术报告还没做。”
→ Personal State

如果描述长期有效的决定：

“我们决定客户端使用 ArkTS。”
→ Semantic Memory

如果描述历史经验：

“上次汇报因为只拼接旧材料导致结构很乱。”
→ Episodic Memory


==================================================
13. Tool Execution
==================================================

Agent 不只提供文字建议。

当用户意图清晰且能力允许时，应通过 Tool 执行真实动作。

V1 目标能力包括：

- Personal State 读取；
- Personal State 修改；
- 创建 / 修改 Task；
- 查询 Deadline；
- Web Search；
- 官方信息查询；
- 图片理解；
- 文档理解；
- 语音处理；
- Automation 创建；
- Automation 修改；
- Push；
- Calendar 操作；
- Source 获取；
- Memory 检索。


--------------------------------------------------
13.1 Tool 行为原则
--------------------------------------------------

Agent 负责：

“应该做什么。”

Tool / Service 负责：

“怎么安全执行。”

用户不需要知道具体调用了哪个函数。

重要副作用操作需要：

- 参数检查；
- 权限检查；
- 幂等；
- 错误处理；
- 必要时用户确认。


==================================================
14. 自主规划与多线并行
==================================================

复杂任务中，Executive Agent 可以动态分解任务。

例如：

“完整看看这个比赛现在什么情况，并告诉我下一步。”

Agent 可以并行：

A. 查询 Personal State
B. 搜索官网
C. 读取最新 PDF
D. 检索历史 Memory

执行完成：

A/B/C/D Results
      ↓
Executive Agent
      ↓
综合
      ↓
验证冲突
      ↓
形成结论
      ↓
必要时更新 Personal State
      ↓
给出下一步


V1 支持的执行策略：

- Direct Response
- Sequential Tool Calls
- Parallel Tool Calls
- Specialist Agent / Subgraph
- Fan-out / Fan-in
- Replan


简单任务不应为了“体现 Agent”而强行复杂化。


==================================================
15. Automation
==================================================

用户可以通过自然语言创建未来动作。

例如：

“明天下午提醒我交报告。”

“截止前两天提醒我。”

“每天帮我检查一次官网有没有更新。”

“这个比赛结果出来之后告诉我。”


Automation 可以包括：

- 一次性时间提醒；
- 周期任务；
- 条件检查；
- Agent Run；
- Push Notification。


系统应允许用户：

- 查看；
- 修改；
- 暂停；
- 删除 Automation。


==================================================
16. Push / Notification
==================================================

当用户没有打开 App 时：

Automation / Important Event
        ↓
Backend
        ↓
Push
        ↓
HarmonyOS Device


Push 的主要场景：

- Deadline；
- Reminder；
- Automation Result；
- Important State Change；
- 用户明确要求的通知。


Push 原则：

- 不滥发；
- 用户可控制；
- 重要信息优先；
- 点击通知后可进入对应 Thing / Chat。


==================================================
17. Calendar
==================================================

V1 希望支持日历能力。

典型行为：

“9月18号下午三点帮我加个答辩。”

Agent：

理解时间和事项
→ 判断是否明确
→ Calendar Tool
→ 创建日历事件
→ 返回结果


如果信息不完整：

“下周提醒我答辩。”

Agent 可以追问必要字段，或者根据 Automation 而不是 Calendar 处理。


==================================================
18. Search
==================================================

Search 是 Agent 的信息获取能力。

区分：

普通 Web Search：
用于公开信息查询。

Official Search：
当事实需要高可信来源时，优先查：

- 官方网站；
- 官方通知；
- 官方文档；
- 官方公告。


例如：

“老师说比赛可能延期。”

如果当前 Personal State 中已有正式 Deadline，而用户使用“可能、好像、听说”等不确定表达：

系统不应立即覆盖正式 Deadline。

可以：

Agent
→ 搜索官方来源
→ 核实
→ 更新状态


==================================================
19. 关键产品行为
==================================================

--------------------------------------------------
Case A：明确状态更新
--------------------------------------------------

用户：
“Demo做完了。”

前提：
存在唯一相关 Thing 和 Task。

期望：

- 正确识别对应 Task；
- 更新 DONE；
- 更新 Thing Progress；
- 记录 Timeline；
- 简洁确认。


--------------------------------------------------
Case B：不确定事实
--------------------------------------------------

用户：
“老师说比赛好像延期到22号。”

当前：
deadline = 9/19

期望：

- 识别“好像”为不确定；
- 不立即覆盖正式 Deadline；
- 根据场景搜索官方来源或询问；
- 核实后才更新。


--------------------------------------------------
Case C：跨对话回忆
--------------------------------------------------

用户新建 Thread：

“我们之前给这个项目定的客户端是什么？”

期望：

- 检索相关 Memory；
- 找到已确定的技术决定；
- 直接回答；
- 不要求用户复制旧聊天。


--------------------------------------------------
Case D：复杂任务并行
--------------------------------------------------

用户：

“把这个比赛彻底梳理一下，看看官网、通知和我们当前进度。”

期望：

- 分解任务；
- 并行读取相关数据；
- 融合结果；
- 识别冲突；
- 给出当前状态和下一步。


--------------------------------------------------
Case E：主动提醒
--------------------------------------------------

当前：
重要任务今天截止并且 TODO。

用户正在进行普通聊天。

期望：

- 正常回应用户；
- 如果当前时机合适，可以自然提醒；
- 如果刚提醒过，则不重复。


--------------------------------------------------
Case F：用户没打开 App
--------------------------------------------------

Automation 到期。

期望：

- 后台触发；
- 执行必要逻辑；
- Push；
- 点击 Push 进入相关内容。


==================================================
20. 异常与模糊场景
==================================================

--------------------------------------------------
20.1 找不到 Thing
--------------------------------------------------

用户：

“Demo做完了。”

但系统有多个可能的 Demo。

Agent 应：

- 使用上下文判断；
- 如果仍然不确定，询问用户；
- 不随机修改。


--------------------------------------------------
20.2 Tool 执行失败
--------------------------------------------------

例如：

Calendar API 失败。

系统应：

- 不假装成功；
- 保留失败结果；
- 说明未完成；
- 可以重试或给用户选择。


--------------------------------------------------
20.3 网络中断
--------------------------------------------------

长任务执行过程中网络断开：

- Server Run 不应因为客户端断开而立即丢失；
- 用户重新进入后可以看到当前状态；
- 必要时恢复 Thread / Run。


--------------------------------------------------
20.4 Agent 更新错误
--------------------------------------------------

用户：

“不是这个比赛，我说的是另一个。”

系统应支持：

- 修正 Personal State；
- 保留状态变化历史；
- 更新 Agent 当前 Context。


--------------------------------------------------
20.5 文件无法解析
--------------------------------------------------

系统应明确告诉用户：

- 文件损坏；
- 格式暂不支持；
- 内容无法提取；
- 或需要其他处理方式。

不能凭空生成文件内容。

23. V1 验收标准 / Eval Cases
==================================================

以下 Case 后续应逐步自动化。

--------------------------------------------------
E01 状态更新
--------------------------------------------------

Given：
Thing A 中 Demo = TODO

When：
用户：“Demo做完了。”

Then：
Demo = DONE
且其他 Task 不受影响。


--------------------------------------------------
E02 状态查询
--------------------------------------------------

When：
“这个项目现在还剩什么？”

Then：
根据 Personal State 返回当前 Pending Tasks / Next Actions。


--------------------------------------------------
E03 不确定 Deadline
--------------------------------------------------

When：
“听说截止日期改22号了。”

Then：
不应未经验证直接修改正式 Deadline。


--------------------------------------------------
E04 新 Thread 继续
--------------------------------------------------

Given：
旧 Thread 已确认某项长期决定。

When：
用户在新 Thread 中询问。

Then：
系统可通过 Long-term Memory 恢复。


--------------------------------------------------
E05 文件关联
--------------------------------------------------

Given：
用户分享与 Thing A 有关的 PDF。

Then：
系统能理解其内容，并根据 Context 关联 Thing A。


--------------------------------------------------
E06 文件产生状态变化
--------------------------------------------------

PDF 中出现新的正式 Deadline。

Then：
Agent 能识别变化，并按 Policy 判断是否更新。


--------------------------------------------------
E07 Attention
--------------------------------------------------

Given：
高优先级 Task 今天截止且未完成。

When：
用户进行普通聊天。

Then：
Agent 可以在合适时机提醒。


--------------------------------------------------
E08 Attention 冷却
--------------------------------------------------

Given：
同一事项刚刚提醒过。

Then：
短时间内不重复提醒。


--------------------------------------------------
E09 Automation
--------------------------------------------------

When：
用户：“明天下午提醒我提交。”

Then：
成功创建 Automation。


--------------------------------------------------
E10 Push
--------------------------------------------------

Given：
用户未打开 App。

When：
Automation 到期。

Then：
手机收到 Push。


--------------------------------------------------
E11 Parallel Execution
--------------------------------------------------

When：
用户要求同时查询官网、文件和当前进度。

Then：
能够并行执行独立任务并统一融合。


--------------------------------------------------
E12 Tool Failure
--------------------------------------------------

Given：
某 Tool 返回失败。

Then：
Agent 不应声称操作已经成功。


--------------------------------------------------
E13 多 Thing 歧义
--------------------------------------------------

Given：
多个项目存在名为 Demo 的 Task。

When：
用户：“Demo完成了。”

Then：
上下文不足时必须澄清，不能随机修改。


--------------------------------------------------
E14 Memory / State 边界
--------------------------------------------------

当前任务完成情况应来自 Personal State，而不是从旧 Memory 猜测。


--------------------------------------------------
E15 Source 保留
--------------------------------------------------

用户上传文件后：

系统应保存 Source 引用，而不是只保存模型摘要。

24. V1 优先级原则
==================================================

尽管 V1 希望覆盖较完整的产品能力，开发顺序仍应遵循：

先核心闭环
→ 再体验增强
→ 再高级能力


推荐核心闭环：

Chat
→ Thing
→ Personal State
→ Tool
→ Thread
→ Memory
→ Multimodal
→ Attention
→ Automation
→ Push


并行进行：

HarmonyOS UI
+
FastAPI / Agent Backend


如果某个高级能力影响正式上架时间，应优先保证：

1. App 稳定；
2. 核心闭环成立；
3. 数据不乱；
4. Agent 不做错误副作用；
5. 产品体验完整。


==================================================
25. 产品原则总结
==================================================

1. 用户使用自然语言，不要求学习系统命令。

2. Thing 表示持续现实事务，不把产品退化成 Todo List。

3. Personal State 是当前现实状态的权威来源。

4. Long-term Memory 保存跨对话的长期信息与经验。

5. Agent 每次只获取当前真正相关的 Context。

6. Agent 可以自主决定直接回答、Tool、并行、Delegation 或追问。

7. 多模态内容必须进入事务闭环，而不是只做总结。

8. 系统主动但不过度打扰。

9. 用户不在线时，Automation + Push 保持系统连续性。

10. 用户始终能够看到和修正系统维护的现实状态。

11. Tool 的真实执行结果优先于模型猜测。

12. 简单任务保持简单，复杂任务才使用复杂执行策略。

13. 所有核心功能都应配套验收 Case。

14. V1 的最终目标是形成一个可以真实长期使用的 HarmonyOS Agent 产品。


==================================================
26. 当前结论
==================================================

老实人 V1 的产品核心不是“聊天页面”。

它的核心产品对象是用户正在持续经历和推进的现实事务。

Chat 是自然输入和决策入口；
Things 是当前现实状态；
Timeline 是重要变化过程；
Memory 是跨对话长期上下文；
Source 是现实信息来源；
Attention 是当前值得关注的问题；
Automation 是未来继续行动的机制；
Tools 是系统真正推进事情的能力。

整体产品闭环：

用户现实世界
   ↓
文字 / 图片 / 文件 / 语音 / Share
   ↓
Executive Agent
   ↓
理解当前事务
   ↓
Context / State / Memory / Source
   ↓
Decision
   ↓
Tool / Action
   ↓
Personal State 更新
   ↓
Timeline
   ↓
Attention / Automation
   ↓
未来继续推进


本 PRD 作为老实人 V1 产品层基线。

后续如果产品需求发生重大变化，应同步更新本文件。
