1. 当前项目理解
==================================================

1.1 App 是什么

“老实人”不是聊天 Demo，也不是普通 Todo App，而是持续理解、记录并推进用户现实事务的 HarmonyOS 个人智能体。核心对象是 Thing；Personal State 是当前现实状态的权威来源，Long-term Memory 保存跨对话仍有价值的历史信息与经验。Executive Agent 通过 Application 用例和 Tool 推进事务，必要时追问、确认、并行或恢复执行。

1.2 核心用户场景

- 用户用自然语言、图片、截图、PDF、Word、PPT、音频或其他 App 分享内容输入现实信息。
- Agent 把输入关联到 Thing，维护 Task、Deadline、Blocker、Next Action、Source、Timeline 和状态历史。
- 用户从 Today 查看当前最重要事项，从 Things/Thing Detail 查看和修正现实状态，从 Chat 与 Agent 持续交互。
- 用户离开 App 后，Automation 在后端继续运行，并通过 Push 主动触达。
- 高风险或含歧义的状态写入、日历等副作用需要用户确认；Run 可中断、恢复，网络断开不应丢失服务端执行。

1.3 计划中的主要页面

- 一级入口：Today、Things、Chat、Me/Settings。
- 业务页面：Thing Detail、Timeline、Source Preview、Automation、Thread List、Share Intake。
- 交互状态：文件上传、流式回答、Run 状态、input-required/确认、冲突、失败、断网重连、空状态、骨架屏。

1.4 实际完成情况（以代码为准）

已完成：
- 后端模块化单体骨架；bootstrap.py 组装依赖，main.py 保持轻薄。
- Personal State：Thing、Task 状态机、ThingDate/正式 Deadline、Blocker、ThingRelation、StateMutation、Timeline、History、乐观并发与幂等。
- Source：受控上传、文件类型/大小/basic magic bytes 校验、对象存储 port、本地 adapter、Thing 关联。
- Long-term Memory：Profile/Semantic/Episodic、生命周期、关键词/元数据/pgvector 检索、provenance。
- Automation/Attention：规则与调度数据、到期领取、NotificationOutbox、Recording Adapter、反馈去重/冷却。
- Product API 与集成测试；OpenAPI 契约已生成。

尚未完成：
- HarmonyOS 客户端：apps/harmonyos 当前只有 README，占位目录中没有 DevEco 工程或 ArkTS 代码。
- Thread/Message/Run/SSE、interrupt/resume、Executive Agent、LangGraph Runtime、Agent Tool Adapter。
- Push Kit 真实 Adapter、设备注册与 token 更新。
- 文件/PDF/Office 内容解析、OCR、图片理解、语音识别/音频理解。
- Account/Auth、Calendar 系统同步、Intents/小艺、服务卡片、应用接续、跨设备能力。

1.5 能力分类

普通 HarmonyOS UI/工程能力：ArkTS、ArkUI、Stage 模型、Navigation、状态管理、MVVM、List/LazyForEach、Skeleton、RichEditor、响应式布局、Preferences、网络层、生命周期、权限和错误处理。

系统服务能力：Core File Kit、PhotoAccessHelper、Share Kit、Core Speech Kit、Core Vision Kit、PDF Kit、Account Kit、Push Kit、Calendar Kit、Form Kit、App Linking、Intents Kit、应用接续、跨设备剪贴板；Live View Kit 仅在严格场景满足时使用。

必须保留为项目自研的核心：Personal State/Memory 边界、Thing/Deadline/Timeline 领域规则、Agent Planner/Memory/Tools/Evidence、LangGraph durable runtime、Policy/HITL、Automation 业务语义与后端 Source 理解管线。


2. 调研方法
==================================================

1）完整核对七份 v1.0 核心设计文档、README、ADR、工程目录、后端依赖、路由、领域枚举、迁移和测试。
2）以“应用鸿蒙化一纸禅”为一级索引，沿模板与组件、Samples、Kits、最佳实践、行业解决方案下钻。
3）以项目真实缺口生成关键词，优先查 developer.huawei.com 的最新指南、API 参考、FAQ、Kit 产品页和行业页。
4）将每项能力按“直接复用 / 修改后复用 / 只参考 Sample / 使用 Kit 接入 / 暂不建议 / 必须自研”分类。
5）凡涉及动态市场、API Level、权限、设备、地区、企业资质或开放审核，均在接入前设置二次核验点。

说明：“一纸禅”、生态市场和 Samples 首页为动态页面，自动抓取有时无法取得正文。本次通过华为官方激励计划说明、具体 Kit/指南/FAQ、模板组件专区和行业方案页交叉核验。市场条目实际下载内容及许可证仍需登录官方页面确认。

6. HarmonyOS Kits
==================================================

6.1 Core File Kit + PhotoAccessHelper（强烈建议）

解决：用户授权的文档、音频、图片选择与保存。
当前需求：PDF/Word/PPT/文本/图片/音频导入。
当前实现：后端已有 Source 上传，客户端没有 Picker。
建议：客户端 common/platform 下实现 FilePickerService、PhotoPickerService；URI 只在授权生命周期内读取/流式上传，服务端继续验证内容。
架构影响：无。只增加客户端 Adapter，不改变 Source Domain/Application。
注意：DocumentViewPicker 推荐使用带 UIAbilityContext 的 API 12+ 构造器；旧 picker.PhotoViewPicker 已废弃。目标 SDK 确定后以最新中文 API 为准。

6.2 Share Kit（强烈建议）

解决：跨应用/跨端分享文本、图片、视频和文件；接收其他 App 分享。
当前需求：Share Intake 是核心入口。
建议：ShareReceiver 解析 Want/SharedData/UTD，转成客户端 Intake DTO，再调用 Source 上传或 Chat 用例。冷启动和热启动都真机测试。
架构影响：无。Share 只产生输入，不直接创建/修改 Thing；业务关联仍由 Application/Agent 决定。
风险：URI、content、权限、记录数量、缩略图大小和 2in1 差异；不信任扩展名和发送方 MIME。

6.3 PDF Kit（强烈建议用于预览）

解决：PDF 解析/预览、缩放、跳页、批注、书签和格式转换。
当前需求：Source Preview、PDF Evidence 查看。
建议：Source Preview 直接采用 PdfView；V1 不自研 PDF 渲染器。后端仍负责全文抽取、结构化、引用定位和 Agent 证据链。
风险：确认目标 API、服务开通/依赖和大文件内存；Web PDF 方案官方提示可能掉帧，不作为主方案。

6.4 Preview Kit（建议评估）

解决：便捷预览文件；openPreview 接收 URI，不接收普通沙箱路径。
官方 FAQ：https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/preview-faq-1-V13
当前需求：Word/PPT 等原文件快速查看。
建议：对支持格式做能力矩阵验证。PDF 用 PdfView；Office/其他格式可优先 Preview Kit 或系统文件处理 App，避免 V1 自研渲染器。
风险：支持格式、设备与 URI 权限在目标 SDK 上待确认。

6.5 Core Speech Kit（强烈建议）

解决：实时或文件音频转文字；短语音不超过 60 秒，长语音不超过 8 小时。
当前需求：麦克风输入转 Composer 文本。
建议：VoiceService 负责录音/识别生命周期，结果只填入 Composer，用户确认发送。音频 Source 的深层理解仍走后端。
风险：不支持模拟器；权限应在用户点击麦克风时动态申请；语言、噪声和设备差异需真机测试。

6.6 Core Vision Kit / Vision Kit（条件接入）

解决：通用 OCR；Vision Kit 另提供文档扫描和 AI 识图控件。
官方入口：https://developer.huawei.com/consumer/cn/sdk/core-vision-kit
限制依据：https://developer.huawei.com/consumer/en/doc/harmonyos-guides-V13/core-vision-introduction-V13
数据说明：https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/corevisionkit-personal-data
当前需求：截图/文档照片取字、可选扫描入口。
建议：端侧 OCR 作为“快速提取文本/预填”能力；原图仍可作为 Source 上传，OCR 结果带来源并由后端判断可信度。Vision Kit 文档扫描后续按地区/设备决定。
风险：OCR 只支持指定图片格式/语言，印刷体优于手写，不支持模拟器；Vision Kit 部分能力仅中国大陆。隐私政策需告知数据处理。

6.7 Account Kit（强烈建议，但需账号决策）

解决：华为账号登录、静默登录、一键登录和统一身份标识。
官方入口：https://developer.huawei.com/consumer/cn/sdk/account-kit
最新概述：https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/account-quick-login-overview
当前需求：项目 Auth 尚未实现。
建议：以 Account Kit 作为客户端认证入口，后端新增 Auth Adapter 验证授权码/ID Token并绑定 user。OpenID/UnionID 映射不能只保存在客户端。
风险：一键登录仅企业开发者；华为账号登录和静默登录支持个人/企业。最终方案取决于开发者账号类型、隐私设计和后端会话策略。

6.8 Push Kit（强烈建议）

解决：后端到 HarmonyOS 设备的远程通知。
官方入口：https://developer.huawei.com/consumer/cn/sdk/push-kit/
服务端鉴权：https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/push-jwt-token
当前需求：Automation/Attention 已生成 NotificationOutbox，但只有 Recording Adapter。
建议：在 backend Infrastructure 新增 HuaweiPushAdapter；凭据/JWT 仅服务端保存。客户端 PushService 获取/更新标识并调用设备注册 Application 用例；点击后通过 App Linking/Navigation 打开目标 Thing/Thread。
架构影响：完全符合现有 port/adapter 设计，不改变 Domain 或 Agent Runtime。
风险：HarmonyOS NEXT/5.x+ 使用 v3 接口；订阅/通知授权、token 变化、送达回执、重复消息和点击幂等需设计。Outbox“提交 adapter”不可宣称已送达。

6.9 Calendar Kit（条件接入，不替代 Automation）

解决：系统日历和日程管理。
官方总目录：https://developer.huawei.com/consumer/cn/doc/?istab=1
API 错误码入口：https://developer.huawei.com/consumer/cn/doc/harmonyos-references/calendar-arkts-errorcode
当前需求：PRD 有 Calendar；正式 Deadline 已在后端实现。
建议：仅当用户明确要求“写入系统日历”时，由 Agent/客户端调用专门 Application 用例，经 Policy/确认后通过 Calendar Adapter 执行并保存外部事件 ID。普通 Deadline 和 Automation 不自动复制到系统日历。
风险：权限、重复日程、删除/更新同步和双向冲突；绝不能让 Calendar 反向无条件覆盖 Personal State。

6.10 Form Kit 服务卡片（建议第二阶段接入）

解决：桌面/锁屏展示重要信息和快捷直达。
官方简介：https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/formkit-overview-V13
当前需求：Today/Attention 的低打扰主动触达。
建议：展示后端返回的 Attention 摘要、最近 Thing、快捷打开 Chat；卡片内写操作也必须调用 Application API。
风险：更新频率、数据过期、隐私可见性、卡片包形态和尺寸适配。卡片不能缓存完整 Personal State。

6.11 Intents Kit + 小艺（建议作为系统入口）

解决：把应用功能声明给系统/小艺，实现自然语言任务、信息查询和一步直达。
官方场景：https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/intents-skill-all-rec-scene-experience
InsightIntent API：https://developer.huawei.com/consumer/cn/doc/harmonyos-references-v5/intents-arkts-api-insightintent-V5
上架配置：https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V5/intents-kit-listing-configuration-V5
当前需求：系统入口、打开 Today/Thing/Chat、触发受控 Agent 请求。
建议：先开放低风险、边界清楚的意图，如“打开 Today”“查看某 Thing”“开始与老实人对话”。带写入或外部副作用的意图把参数传入 App/Agent Adapter，继续走后端 Run/Policy/HITL。
架构影响：Intents 是入口和 Adapter，不是 Planner/Memory/Tool Runtime。
风险：正式上线需 App 先上架 AGC，并在小艺开放平台审核；自测试能力和版本门槛随 HarmonyOS 6/API 20+ 演进，接入时重新核验。

6.12 App Linking（强烈建议）

解决：HTTPS 链接安全拉起指定应用页面；未安装时也可进入网页。
官方指导：https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V14/app-linking-startup-V14
当前需求：Push、分享、二维码、小艺使用统一深链。
建议：以 App Linking 作为外部正式链接，内部统一映射到 Navigation route；自定义 scheme 只作开发或兼容备选。
风险：HarmonyOS 应用 API 12+；需要 AGC、域名关联和服务器验证配置。

6.13 跨设备剪贴板 / 应用接续（建议后续）

解决：跨设备复制素材；把同一应用操作状态从一个设备接到另一个设备。
官方链接：https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/distributed-pasteboard-guide-V13
应用接续 FAQ：https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/free-flow-faqs-1
当前需求：多设备输入和长任务连续性。
建议：先用服务端 Thread/Run 恢复形成跨设备基础，再增加剪贴板和应用接续。接续只传页面/资源标识和必要轻状态，不传完整 Agent Graph State。
风险：同一华为账号、Wi-Fi/蓝牙、亮屏/解锁、DISTRIBUTED_DATASYNC 权限及设备组合限制。

6.14 Live View Kit（当前通常不建议）

解决：锁屏、通知中心、状态栏展示最长 8 小时内持续变化的进行中事件。
官方简介：https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/liveview-introduction-V13
当前需求：大部分 Deadline/Attention 是单点提醒，不符合实况窗准入语义。
建议：暂不接。将来只有“用户主动启动、持续一段短时间、状态动态变化且高关注”的 Agent 任务才申请评估。
风险：Phone/Tablet、非模拟器、中国大陆、场景准入和反营销限制；不可把普通长任务或所有 Run 都做实况窗。


7. 官方最佳实践
==================================================

总入口：https://developer.huawei.com/consumer/cn/doc/best-practices/bpta-best-practices-overview

7.1 工程与架构

- Stage 模型是长期演进方向；本项目选择正确。
- 官方分层架构：https://developer.huawei.com/consumer/cn/doc/doccenter-architecture/bpta-layered-architecture-design
- 官方模块化设计：https://developer.huawei.com/consumer/cn/doc/doccenter-architecture/bpta-modular-design
- 项目采用单 entry、feature-first + MVVM 合理。当前规模不要为了“模块化”先拆 HAR/HSP；出现明确复用、独立部署或构建收益时再拆。

7.2 Navigation

- 使用 Navigation + NavDestination + NavPathStack；API 10+ 官方更推荐 NavPathStack。
- Push、Share、App Linking、Intents 和冷启动统一进入同一个路由解析器，避免五套跳转逻辑。
- 路由参数只传资源 ID/轻量 DTO，不传完整实体或 Graph State。

7.3 状态管理与 MVVM

- 官方 MVVM 指导：https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/arkts-mvvm-V13
- 新工程优先评估状态管理 V2；目标 API 确定后锁定装饰器版本，不混用两套全局状态方案。
- ViewModel 管 UI 状态和交互；Repository/ApiClient 管远端数据；Thing 业务规则仍在后端。

7.4 长列表和流式 Chat

- Things、Timeline、Thread 使用 LazyForEach/懒加载、稳定 key、组件复用和分页。
- 性能指导：https://developer.huawei.com/consumer/cn/doc/best-practices-V5/bpta-control-rendering-range-V5
- assistant.delta 不应每个 token 触发整条消息列表重建；做增量缓冲与受控刷新。
- 图片缩略图与 Source 大文件异步加载，避免 UI 主线程解析。

7.5 数据与网络

- Preferences 只存 theme、onboarding、last thread、环境等小型设置；不存完整 Thread/Thing、token 明文或大文件。
- 离线缓存按真实需求使用 ArkData，不复制服务器全部表；缓存应带版本/时间并允许失效。
- 普通 REST 与上传统一 ApiClient；Thread/Run/SSE 的 durable 语义由服务端资源保证。HarmonyOS 网络 API 是否稳定支持目标 SSE 方式需在首轮真机联调验证，必要时选择官方支持的 HTTP 流或 WebSocket，但不改变事件契约。

7.6 权限、隐私和安全

- 官方隐私最佳实践：https://developer.huawei.com/consumer/cn/doc/doccenter-architecture/bpta-app-privacy-protection
- 坚持透明、最小化、用户控制、安全和优先本地处理；权限在功能触发时动态申请，不在首次启动一次性索要。
- 不申请“遍历全盘”式高权限；文件、图片通过系统 Picker 授权。
- 麦克风、通知、分布式同步分别解释用途；拒绝后保留降级路径。
- Provider 密钥、Push 服务账号、数据库凭据和模型密钥绝不进入客户端。

7.7 测试和性能

- Push、Share、文件 URI、Photo Picker、Speech/OCR、后台恢复、Deep Link、权限、大文件上传必须真机。
- 没有真机时可用官方云测试/云调试，但最终仍需目标真机覆盖账号、Push 和跨设备场景。
- 使用 DevEco Profiler 验证冷启动、长列表、内存、网络和主线程耗时；不为了性能提前采用复杂并发。

9. Agent / AI / Intents 相关能力
==================================================

9.1 推荐边界

HarmonyOS 系统能力
  -> HarmonyOS App / Intents / AgentAbilityExtension
  -> Agent Adapter
  -> 现有后端 API（Thread/Run/Resume/Tool contracts）
  -> LangGraph Runtime
  -> Planner / Memory / Tools / Evidence / Policy

系统入口层只负责发现、唤起、参数传递、端侧交互和状态呈现。真正的 Agent 计划、长期记忆、现实状态判断、Tool 执行、证据与恢复继续在后端。

9.2 Agent Framework Kit / A2A

官方指南：https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/hmaf-a2a-dev-guide

官方 2026-07-28 指南描述：ArkTS 应用可通过 AgentAbilityExtension 构建 A2A 服务端；A2A 包含 Agent Card（身份、能力、端点、技能、认证元数据）、Artifact，以及 TaskState（submitted、working、input-required、completed、cancelled、failed、rejected、auth-required 等）。

与项目映射：
- Agent Card -> 可描述“老实人”的能力与认证，但不是 Tool Registry 或 Prompt。
- A2A Task -> 可映射/桥接后端 Run，但不能直接复用同一个状态表；需要明确 ID、状态和错误转换。
- Artifact -> 可映射 Source/生成文档引用，但不能把临时产物自动写成 Personal State。
- input-required -> 映射现有 interrupt.required / WAITING_USER 与客户端确认 UI。
- 用户确认 -> 仍由后端 Policy/HITL 给出权威决策；端侧只呈现和提交 resume payload。
- Agent Discovery -> 只决定系统如何发现/调用客户端 Agent，不替代后端能力注册。

建议：当前只做协议预留和概念映射，不在 Thread/Run/SSE 之前接入。待目标 SDK、设备、账号和开放范围确认后做独立 Spike。不要让 AgentAbilityExtension 直接访问后端 ORM、客户端凭据或本地数据库。

9.3 Intents / 小艺

Intents 比完整 A2A 更适合早期系统入口：先接低风险“打开 Today/查看 Thing/开始对话”；未来再接带参数的任务。任何写状态、发通知、建日程、删除或外部服务操作都继续走 Agent Adapter -> Application/Policy/HITL。

9.4 Core Speech / Core Vision 与 Agent

这些 Kit 是感知 Adapter，不是 Agent。端侧输出应作为用户输入或 Source 派生数据，保留原始来源、能力版本和用户确认。它们不能直接更新 Deadline、Task 状态或 Memory。

【收益】系统日历协同和用户熟悉的提醒体验。
【风险】形成第二提醒系统、重复/冲突、权限和删除同步。

【项目能力】Things/Timeline/Chat 长列表
【官方资源】LazyForEach、组件复用、控制渲染范围最佳实践
【官方链接】https://developer.huawei.com/consumer/cn/doc/best-practices-V5/bpta-control-rendering-range-V5
【当前实现】客户端未实现；后端已有分页/过滤基础。
【建议】作为工程最佳实践直接采用。
【收益】避免长列表掉帧，支持持续使用。
【风险】稳定 key、分页去重、流式消息刷新和图片内存。

【项目能力】页面导航与外部入口
【官方资源】Navigation + NavPathStack + App Linking
【官方链接】https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/arkts-navigation-jump
【当前实现】客户端未实现。
【建议】直接采用；所有入口汇入统一 Router。
【收益】减少跳转分叉和冷启动 bug。
【风险】恢复时资源可能不存在，必须显示可理解的降级页面。

【项目能力】跨设备继续处理
【官方资源】应用接续 + 跨设备剪贴板
【官方链接】https://developer.huawei.com/consumer/cn/doc/harmonyos-guides-V13/distributed-pasteboard-guide-V13
【当前实现】后端 Thread/Run 尚未完成。
【建议】暂缓。先完成服务端 durable Run，再把页面/资源 ID 接续到另一设备。
【收益】后续增强一多体验。
【风险】设备/账号/权限/网络条件；禁止传完整 Graph State。

14. 可能值得调整的现有实现（非本轮代码修改）
==================================================

1）HarmonyOS 设计文档中“优先使用当前官方推荐的 photoAccessHelper.PhotoViewPicker”表述需在建工程时再核对准确类名；可以确定的是 `@ohos.file.picker` 内旧 PhotoViewPicker 已 deprecated，不能照旧示例实现。

2）客户端设计已有 FilePickerService/PhotoPickerService/ShareReceiver/VoiceService/PushService 分层，方向正确。建议增加 AppLinkRouter、AccountService、PdfPreviewService，并把 Intents/A2A 预留为 platform adapter，而不是 feature 业务层。

3）现有 NotificationOutbox 只记录 SUBMITTED_TO_ADAPTER/FAILED。接 Push 前明确“提交华为 Push”与“设备送达/用户点击”不同语义，不要把平台接受响应写成送达成功。

4）Source 当前允许 PDF/PNG/JPEG/DOCX/PPTX/MP3。客户端 Picker 的类型过滤应由后端能力清单或共享 contract 驱动，避免客户端与后端各维护一份漂移名单。

5）Source Preview 应采用“PDF Kit + Preview Kit/系统处理应用 + 图片原生预览”的组合，不建一个万能自研渲染器。

6）语音 V1 采用“识别成文本 -> Composer -> 用户发送”。不要同时建立端侧语音命令引擎和后端 Agent 两套意图判断。

7）Push/Share/Intents/App Linking 应共享一个外部路由解析与幂等入口。设计文档中的自定义 `laoshiren://` 可保留开发用途，生产优先 HTTPS App Linking。

8）Agent Framework TaskState 与后端 RunStatus 需要显式映射文档/ADR；不能复用同名字段制造隐式耦合。


15. 推荐后续开发优先级
==================================================

阶段 A：确定 bundle name、目标 SDK/API、签名、个人/企业开发者账号和真机；逐项确认 Kit 可见性、权益和地区。

阶段 B：创建单 entry Stage 工程，落地 feature-first + MVVM、Navigation/NavPathStack、统一 ApiClient、状态管理和基础设计系统。

阶段 C：完成 Chat/Things/Thing Detail/Today 的纯 API 闭环；同时用官方长列表、骨架屏、权限和隐私最佳实践。

阶段 D：接 Core File/Photo Picker、Share Intake、PDF/Preview，复用现有 Source API；真机验证 URI、冷/热启动和大文件。

阶段 E：接 Core Speech；按需要试验 Core Vision OCR。两者都作为输入 Adapter，不直写 State。

阶段 F：后端完成 Thread/Run/SSE/LangGraph/HITL 后，客户端完成流式、input-required、resume 和断线恢复。

阶段 G：确定 Auth 后接 Account Kit；随后用 Push Kit 替换 Recording Adapter，并接 App Linking。

阶段 H：接服务卡片和低风险 Intents；根据真实使用再评估 Calendar、应用接续、跨设备剪贴板。

阶段 I：Agent Framework/A2A 独立 Spike。确认 API Level、设备、权限、审核和安全后，才决定是否产品化；LangGraph 不迁移到客户端。

结论
==================================================

华为官方已经替本项目解决了大量“手机系统入口与通用客户端能力”：文件/图片选择、跨应用分享、PDF 渲染、语音识别、OCR、账号、Push、深链、桌面卡片、意图入口、基础导航/状态管理/长列表/隐私实践。这些能力应作为 HarmonyOS platform Adapter 或后端 Infrastructure Adapter 接入。

官方没有替项目解决、也不应替换的是“老实人”的产品核心：Personal State、Memory、Thing、Evidence、Automation 语义、Policy/HITL 和 LangGraph Agent Runtime。正确的鸿蒙化不是把后端大脑搬到端上，而是用 HarmonyOS 官方能力让用户更自然地输入、查看、唤起、确认、跨场景继续并被恰当地触达。
