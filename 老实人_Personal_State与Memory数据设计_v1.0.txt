《老实人｜Personal State + Memory 数据设计 v1.0》

版本：v1.0
项目名称：老实人
文档类型：Domain State & Memory Data Design
当前阶段：V1 正式开发设计
目标：定义 Personal State、Thing、Task、Deadline、Timeline、Source、Long-term Memory 的数据边界与核心结构

==================================================
0. 文档目的
==================================================

本文件用于确定老实人 V1 的“数据大脑”。

重点回答：

1. 用户现实中的一件事情如何表示；
2. Thing、Task、Deadline、Status、Progress、Next Action 如何组织；
3. Personal State 保存什么；
4. Long-term Memory 保存什么；
5. Thread Memory 与 Long-term Memory 的边界；
6. Timeline 保存什么；
7. Source 如何与事务关联；
8. Agent 如何读取和修改这些数据；
9. 如何避免同一个事实在 State 和 Memory 中产生冲突；
10. 如何为后续 Attention、Automation、Retrieval 和 Eval 提供稳定数据基础。

核心原则：

Personal State = 当前现实状态
Long-term Memory = 跨对话长期信息与经验
Thread State = 当前对话运行上下文
Timeline = 重要变化过程
Source = 原始现实信息来源

这五者必须分开。


==================================================
1. 总体数据分层
==================================================

老实人 V1 的数据可分为五层：

A. Runtime / Thread Layer
B. Personal State Layer
C. Long-term Memory Layer
D. Source / Timeline Layer
E. Automation Layer


总体关系：

User
 │
 ├── Threads / Messages
 │
 ├── Things
 │     ├── Tasks
 │     ├── Deadlines
 │     ├── Next Actions
 │     ├── Blockers
 │     ├── Related People
 │     ├── Related Sources
 │     └── Timeline Events
 │
 ├── Long-term Memories
 │     ├── Profile
 │     ├── Semantic
 │     └── Episodic
 │
 ├── Sources
 │
 └── Automations


==================================================
2. Personal State 定义
==================================================

Personal State 是：

“用户现实事务当前状态的权威存储。”

它必须回答：

- 用户现在有哪些事情；
- 每件事情现在处于什么阶段；
- 当前有哪些任务；
- 哪些已完成；
- 哪些未完成；
- 当前截止日期是什么；
- 当前最大的阻碍是什么；
- 下一步应该做什么；
- 哪些事情正在等待别人；
- 哪些状态最近发生变化。

Personal State 不负责：

- 保存完整聊天记录；
- 保存所有过去版本的全文；
- 保存用户所有历史经验；
- 保存未来调度器；
- 保存大文件内容；
- 保存模型推理过程。


==================================================
3. Thing 作为核心领域对象
==================================================

Thing 表示一个需要持续维护的现实事务。

例如：

- 一个比赛；
- 一个项目；
- 一篇论文；
- 一门课程；
- 一份申请；
- 一段实习任务；
- 一次旅行计划；
- 一个长期目标。

Thing 不是 Task。

Task 通常是 Thing 内部可执行的具体工作。


示例：

Thing：
鸿蒙应用开发者激励计划

Tasks：
- 学习 ArkTS
- 完成 Chat 页面
- 接入 FastAPI
- 完成上架材料
- 提交审核

5. Thing Type
==================================================

V1 不为每一种现实事务创建独立数据库表。

统一使用 Thing Core
+
Type-specific extension。


建议基础类型：

PROJECT
COMPETITION
COURSE
PAPER
WORK
APPLICATION
PLAN
EVENT
PERSONAL
OTHER


类型的意义主要用于：

- Skill Resolution；
- UI 表达；
- 推荐字段；
- Attention Rule；
- Search Filter。


不要让 type 变成强限制。

一个现实事项如果暂时无法分类：

即可。


==================================================
6. Thing Status
==================================================

建议 V1 使用有限状态集：

PLANNING
ACTIVE
BLOCKED
WAITING
PAUSED
COMPLETED
CANCELLED
ARCHIVED


说明：

PLANNING
- 已创建，但还在规划。

ACTIVE
- 正在推进。

BLOCKED
- 当前存在明确阻碍。

WAITING
- 当前主要等待外部人/事件。

PAUSED
- 主动暂停。

COMPLETED
- 事务完成。

CANCELLED
- 终止，不再推进。

ARCHIVED
- 历史归档。


状态不要设计得过细。

更具体的阶段：

用 current_stage 表达。


例如：

status = ACTIVE
current_stage = “正式开发”

而不是创造：

DEVELOPING_FRONTEND
DEVELOPING_BACKEND
WAITING_REVIEW
...


==================================================
7. Priority
==================================================

建议：

LOW
NORMAL
HIGH
URGENT


优先级来源可以有两种：

user_defined_priority
agent_inferred_priority


最终展示：

effective_priority


原则：

用户明确设置 > Agent 推断。


Agent 可以根据：

- deadline proximity；
- importance；
- blocker；
- dependencies；
- user language；

建议提升优先级。

但除非 Policy 允许，不应频繁自行改变用户明确设置的优先级。


==================================================
8. Progress
==================================================

Progress 不建议只存 0-100%。

因为很多现实事务无法准确量化。

建议：

progress_mode

可选：

TASK_BASED
PERCENTAGE
STAGE_BASED
MANUAL
UNKNOWN


字段：

progress_value
progress_summary


例如：

progress_mode = TASK_BASED
progress_value = 0.65

或：

progress_mode = STAGE_BASED
progress_summary = “已进入正式审核准备阶段”


UI 可以根据不同类型选择不同表达。

10. Deadline / Important Date
==================================================

一个 Thing 可能不止一个日期。

因此：

Thing.deadline_at

只作为“当前主要截止日期”的快捷字段。

同时应有：

ThingDate


建议：

ThingDate
├── id
├── thing_id
├── label
├── kind
├── starts_at
├── ends_at
├── is_primary
├── certainty
├── source_id
├── status
├── created_at
└── updated_at


kind 例如：

REGISTRATION_DEADLINE
SUBMISSION_DEADLINE
REVIEW_DATE
MEETING
EXAM
RESULT_DATE
CUSTOM


certainty：

CONFIRMED
PROBABLE
UNCONFIRMED
DISPUTED


这非常重要。

例如：

“老师说好像延期到22号。”

可以先保存为：

candidate date
certainty = UNCONFIRMED

而不是直接覆盖：

Thing.deadline_at。


正式验证后：

certainty = CONFIRMED
is_primary = true
Thing.deadline_at = 9/22

11. Next Action
==================================================

Next Action 是 Agent 很重要的当前状态。

Thing 可以有多个 Action Candidate，
但应尽量明确一个：

primary_next_action


V1 可以直接从 Task 派生，
也可以单独维护：

NextAction
├── thing_id
├── task_id
├── summary
├── reason
├── priority
├── suggested_at
└── status


V1 为避免模型过重：

建议先不单建复杂 NextAction 表。

优先采用：

Task
+
Thing.next_action_summary

后续出现需要再升级。

StateMutation

├── action_id

==================================================
19. 当前状态的权威来源
==================================================

一个非常重要的规则：

Current Operational Truth
=
Personal State


例如：

Task:
技术报告

Current Status:
DONE


即使某条旧 Memory 写着：

“技术报告还没完成。”

也不能回答：

“还没完成。”


优先级：

Personal State
>
Recent verified Tool Result
>
Current Source
>
Long-term Memory
>
Old Conversation Text


Memory 不能覆盖当前业务状态。


==================================================
20. Thread Memory
==================================================

Thread Memory 由 LangGraph Checkpoint / State 管理。

主要包含：

- messages；
- working plan；
- tool results；
- pending actions；
- interrupt；
- runtime state。


Thread Memory 生命周期：

围绕 Thread 持续。

但不承担：

跨 Thread 用户知识库。


例如：

Thread A 中：

用户：
“Demo做完了。”

Task 更新后：

当前状态进入 Personal State。

用户新开 Thread B：

不需要复制 Thread A 全部消息。

Thread B 可以直接读取：

Personal State:
Demo = DONE

==================================================
22. Profile Memory
==================================================

Profile Memory 表示相对稳定的用户偏好和长期特征。

例如：

“用户偏好简洁直接的提醒。”
“用户不喜欢同一个提醒频繁重复。”
“用户经常同时推进多个项目。”


Profile Memory 不应保存：

“今天报告没写完。”

因为这不是稳定信息。


Profile 可以采用两层：

A. Core Profile

少量稳定字段，可直接预加载。

B. Profile Memories

更细碎的长期偏好，通过检索加载。


==================================================
23. Semantic Memory
==================================================

Semantic Memory 表示跨 Thread 仍有长期价值的事实、决策和关系。

例如：

“老实人 V1 决定采用单一 Executive Agent。”
“客户端采用 ArkTS + ArkUI。”
“Personal State 不作为固定 Graph Node。”
“Competition Skill 中应区分报名截止和提交截止。”


Semantic Memory 适合：

- 技术决定；
- 长期规则；
- 稳定事实；
- 重要关系；
- 经过确认的结论。


==================================================
24. Episodic Memory
==================================================

Episodic Memory 表示过去发生的重要经历。

例如：

“上一次正式汇报时，先重新根据老师要求搭故事线，比直接拼旧 PPT 效果更好。”

“上次某个 Tool 因重复执行导致创建了两个相同日历事件，后来加入 idempotency key。”


它强调：

过去发生过什么
+
结果如何
+
未来类似场景有什么参考价值。


==================================================
25. Memory 与 Timeline 的区别
==================================================

Timeline：

记录“发生过什么”。

Memory：

记录“未来还值得记住什么”。


例如：

Timeline：

8/23
确定 Agent 架构采用单一 Executive Agent。


Memory Formation 后：

Semantic Memory：

“老实人架构已确定以单一 Executive Agent 为全局交互和决策核心。”


并不是每条 Timeline 都必须形成 Memory。


==================================================
26. Memory 与 Source 的区别
==================================================

Source：

原始来源。

Memory：

从对话和现实事件中抽取出的长期有价值内容。


例如：

Source：

官方 PDF。

Memory：

“官方要求应用必须在 9/30 前正式上架。”


如果未来需要验证：

Memory
→ source reference
→ Source

可以回溯。


==================================================
27. Memory Formation
==================================================

推荐：

不要每轮用户消息都立即调用一次 Memory LLM。


使用：

Event Buffer
↓
Debounce / Batch
↓
Memory Formation Worker
↓
Extract Candidates
↓
Compare Existing Memories
↓
Decide:
  Profile Update
  Semantic Upsert
  Episodic Insert
  Ignore


输入至少包含：

- 最近对话；
- 当前相关 Thing；
- 最近 State Mutation；
- Existing Relevant Memories。


这样 Memory Manager 能知道：

“哪些信息已经在 Personal State 中维护，不应该重复写成当前状态 Memory。”


==================================================
28. Memory Formation Candidate
==================================================

Memory Manager 可以先生成 Candidate：

MemoryCandidate
├── memory_type
├── content
├── reason
├── importance
├── confidence
├── thing_id
├── source_refs
└── action


action：

CREATE
UPDATE
MERGE
SUPERSEDE
IGNORE


例如：

输入：

“以后重要比赛都提前三天提醒我。”

Candidate：

type = PROFILE
content = 用户偏好重要比赛截止前3天收到提醒
action = CREATE


输入：

“Demo做完了。”

Personal State 已更新：

Demo = DONE

Memory Candidate：

IGNORE

因为这是当前状态，不需要再作为长期事实复制。


==================================================
29. Memory 更新与合并
==================================================

Memory 不是只增不改。


例如：

旧 Profile Memory：

“用户喜欢截止前一天提醒。”

新明确表达：

“以后重要事情提前三天提醒。”


可以：

old memory
→ SUPERSEDED

new memory
→ ACTIVE


或直接 update。


Semantic Memory 也可能变化：

旧：

“项目采用多 Agent。”

新：

“最终架构改为单一 Executive Agent。”


应该：

旧 Memory 标记 superseded
+
新 Memory active


避免检索时同时返回两个互相冲突的结论。

==================================================

user_id

thing_id

==================================================
34. Memory Embedding
==================================================

Embedding 主要用于：

Semantic
Episodic
可检索 Profile Memory


Embedding 不用于：

所有数据库字段。


Personal State 的结构化字段：

优先 SQL / Filter / Search。

不要：

“找今天截止任务”

SQL:
deadline <= today

==================================================
35. Personal State Retrieval
==================================================

Personal State 查询优先结构化方式：

state.search_things
state.get_thing
state.get_tasks
state.get_deadlines
state.get_history


查询维度：

- exact ID；
- name；
- type；
- status；
- deadline；
- priority；
- relation；
- full-text / fuzzy name search。


如果用户说：

“之前那个鸿蒙比赛”

可以：

Text/Fuzzy Search
+
Thread hints
+
Recent Thing usage


找候选 Thing。


==================================================
36. Active Thing Resolution
==================================================

Context Builder 可以维护：

active_thing_refs


来源：

- Thread 最近讨论；
- 用户明确名称；
- 分享 Source 的历史关联；
- 最近访问 Thing；
- 搜索匹配。


建议输出：

ThingCandidate
├── thing_id
├── confidence
└── reason


高置信：

可自动 prefetch。


低置信：

让 Agent 继续判断。


多个高相似候选：

不要随机修改。


==================================================
37. State Update Policy
==================================================

State Mutation 按风险划分。


LOW RISK

例如：

用户明确：
“Demo做完了。”

且唯一定位 Task。

可以直接更新。


MEDIUM RISK

例如：

“我准备下周把报告做完。”

这是计划，不是完成状态。

可以：

创建/更新 Task target date

但不能：

Task = DONE


HIGHER UNCERTAINTY

例如：

“听说截止时间改了。”

不能直接覆盖 verified deadline。

应验证或询问。


==================================================
38. Fact Certainty
==================================================

建议对关键事实支持 certainty。


适用：

- deadline；
- eligibility；
- requirement；
- external result；
- important rule。


certainty：

CONFIRMED
PROBABLE
UNCONFIRMED
DISPUTED


正式 Personal State 的主要字段：

优先使用 CONFIRMED。


候选信息可以放：

fact_candidates
或
ThingDate certainty


V1 不需要所有字段都加 certainty。

只对高风险动态事实使用。


==================================================
39. State Conflict
==================================================

可能出现：

用户说 A
官方 Source 说 B
旧 State 是 C


建议冲突处理优先级：

1. 用户对“用户自身行为”的明确陈述；
2. 官方可靠来源对外部事实的明确说明；
3. 已确认 Personal State；
4. 第三方来源；
5. 推测 / Memory。


例如：

用户：
“我已经提交了。”

这是用户自身行为。

可以把：

submission task = DONE

但如果：

用户：
“比赛截止应该是22号。”

这是外部事实。

如果已有官方 19 号：

应验证。


==================================================
40. Optimistic Concurrency
==================================================

Thing / Task 重要写入支持 version。


例：

Thing version = 12

Agent A：
read version 12

Agent B：
read version 12

Agent A：
update
→ version 13

Agent B：
update WHERE version=12
→ conflict


Agent B：

重新读取
→ 判断新状态
→ 必要时重新执行。


避免无条件 Last Write Wins。


==================================================
41. Idempotency
==================================================

State Mutation 使用：

idempotency_key


建议：

run_id + action_id


数据库记录：

同一 idempotency_key 已执行成功

再次调用：

返回原 mutation result。


避免：

Agent resume
网络重试
客户端重复请求

导致：

重复创建 Task
重复创建 Automation
重复状态变化。


==================================================
42. Delete / Archive
==================================================

V1 对重要对象优先：

soft delete / archive


Thing：

archived_at

Memory：

status = DELETED

Automation：

status = CANCELLED


真正物理删除：

后续根据隐私/账户删除需求执行。


原因：

- Agent误操作可恢复；
- Timeline 可追踪；
- Debug；
- 用户撤销。


==================================================
43. Attention 所需数据
==================================================

Attention 不需要独立成为主数据源。

可以从：

Thing
Task
ThingDate
Blocker
Automation
StateMutation

派生。


典型 SQL / Rule：

Task:
status != DONE
AND due_at < now
→ overdue


Task:
due_at today
→ due_today


Thing:
priority = HIGH
AND updated_at < threshold
→ inactive_important


Blocker:
status = OPEN
AND blocked_since < threshold
→ blocked_too_long


再结合：

last_surfaced_at
dismissed_until
acknowledged

决定是否进入 Attention Candidate。

57. Data Integrity
==================================================

==================================================
59. Source Provenance
==================================================

关键状态变化尽量保留来源。

例如：

source_id = ...


Task 完成：

source_type = USER_ASSERTION
source_message_id = ...


Agent 推断：

source_type = AGENT_INFERENCE


重要事实：

尽量可回溯：

“为什么系统认为这是 9/22？”


==================================================
60. Confidence
==================================================

不要给所有数据都增加 AI confidence。

只在真正有意义的位置保留：

- extracted facts；
- unverified external facts；
- memory formation；
- Thing resolution。


例如：

ThingCandidate:
confidence = 0.91

MemoryCandidate:
confidence = 0.85


用户明确陈述：

不需要再给一个假的 0.97。

==================================================
62. 数据隐私基线
==================================================

即使当前本人使用，也要从结构上支持：

- 按 user_id 隔离；
- 删除 Memory；
- 删除/归档 Thing；
- 删除 Source；
- 删除 Automation；
- 账户级数据清理。


Source 原文件和数据库 metadata 要能关联删除。


避免：

数据库删了 Source，
Object Storage 文件仍永久遗留。


==================================================
63. V1 不建议做的事情
==================================================

1. 不把每句话转成一条 Memory。
2. 不把所有 State 同步复制到 Memory。
3. 不用向量数据库查询结构化 Deadline。
4. 不把聊天 Thread 当 Thing。
5. 不把 Timeline 当完整聊天日志。
6. 不为不同 Thing Type 建十几套数据库结构。
7. 不允许 LLM 直接写 SQL。
8. 不用最终一致性掩盖关键状态写冲突。
9. 不做所有信息永久不可修改的 Memory。
10. 不为了“知识图谱”提前引入复杂 Graph DB。

用户：
“这个项目还有什么没做？”

D03

用户：

67. 最终边界总结
==================================================

一句话：

Personal State 管“现在”。

Memory 管“过去值得继续记住的东西”。

Thread 管“当前这段对话正在做什么”。

Timeline 管“事情是怎么变化过来的”。

Source 管“这些信息从哪里来”。

Automation 管“未来什么时候继续行动”。


更完整：

现在：
Personal State

过去：
Long-term Memory

当前对话：
Thread State

变化过程：
Timeline

原始证据/资料：
Source

未来：
Automation


Executive Agent 不拥有这些数据。

Executive Agent 通过 Context + Tool 使用这些数据。

==================================================

老实人的个人数据系统最终形成：

                     User
                      │
         ┌────────────┼────────────┐
         ▼            ▼            ▼
      Threads        Things      Memories
                       │
              ┌────────┼─────────┐
              ▼        ▼         ▼
            Tasks    Dates     Blockers
              │        │
              └────────┼─────────┐
                       ▼         ▼
                    Timeline   Sources
                       │
                       ▼
                 State Mutations

Future:
Automations

Attention:
Derived from Current State


其中：

Timeline / Mutation 描述其变化。

Source 提供现实来源。

Memory 保存跨对话长期价值。

Automation 将未来行动从 Memory 中剥离。

Attention 从当前状态中动态派生。


本文件作为老实人 V1 Personal State + Memory 数据设计基线。

后续数据库 Migration、ORM Model、Repository 和 Tool Schema
