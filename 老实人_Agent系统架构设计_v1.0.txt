《老实人｜Agent 系统架构设计 v1.0》

版本：v1.0
项目名称：老实人
文档类型：Agent System Architecture
当前阶段：V1 正式开发设计
目标平台：HarmonyOS + Cloud Backend
后端主栈：Python + FastAPI + LangGraph
持久化方向：PostgreSQL + pgvector + Object Storage

==================================================
0. 文档定位
==================================================

本文件是“老实人”V1 的 Agent 技术架构基线。

它重点回答：

- 一次用户输入进入系统后，Agent 如何运行；
- Context 如何构造；
- Thread Memory、Long-term Memory、Personal State 如何分工；
- Executive Agent 如何自主决策；
- Tool 如何执行真实动作；
- 如何支持并行 Tool / Specialist Agent；
- 如何暂停、恢复和处理失败；
- Memory Formation、Automation、Ingestion 为什么不进入主 Agent 固定流程；
- LangGraph 在系统中负责什么、不负责什么。

本文件不详细定义：

- 数据库最终表结构；
- Tool 的完整 Function Schema；
- FastAPI API 的完整 Request/Response；
- HarmonyOS 页面实现；
- 最终模型供应商与模型 ID。

这些内容在后续文档继续确定。


==================================================
1. 架构结论
==================================================

老实人采用：

“单一 Executive Agent 为交互与决策核心
+
Context Engineering
+
Tool Runtime
+
Durable Agent Runtime
+
后台 Memory / Automation / Ingestion 服务”

的 Agent-first 架构。


核心形式：

Current Context
      ↓
User Input / System Event
      ↓
Executive Agent
      ↓
Reason / Decide
      ↓
┌─────────────────┬─────────────────┬─────────────────┬─────────────────┐
│                 │                 │                 │                 │
Respond         Ask User          Tool Call        Delegation
│                 │                 │                 │
END            interrupt        Tool Runtime      Specialist
                                    │                 │
                                    └────────┬────────┘
                                             ↓
                                           Result
                                             ↓
                                      Executive Agent
                                             ↓
                                   Synthesis / Replan
                                             ↓
                                    Continue / Respond


系统不采用：

User Input
→ Semantic Extractor
→ State Reconciler
→ Personal State Update
→ Planner
→ Executor

这种固定前置流水线作为主要交互路径。

原因：

现实输入是否应修改状态、是否需要搜索验证、是否只是普通聊天、是否需要进一步理解资料，本身就是 Agent 需要判断的问题。

因此：

Personal State Read
Personal State Write
Memory Search
Perception
Web Search
Automation
Calendar
Notification

全部作为 Agent 可选择的能力，而不是所有请求必经步骤。

2. 官方能力与本项目工程选择的边界
==================================================

为了避免后续把“框架能力”和“老实人自己的设计”混为一谈，本项目明确区分：

【LangGraph 官方提供的基础能力】

- Graph State
- Nodes / Edges
- Conditional Routing
- Checkpoint / Thread Persistence
- interrupt / resume
- Durable Execution
- Parallel Supersteps
- Fan-out / Fan-in
- Send 动态 Map-Reduce
- Reducers
- Subgraphs
- Retry / Fault Tolerance

【成熟 Agent 工程通用思想】

- LLM + Tools Loop
- Hybrid Context Retrieval
- Context Compaction
- Manager / Agent-as-Tool
- Guardrails / Policy
- Tracing / Eval

【老实人项目自己的产品/工程组件】

- Personal State
- Thing
- Attention Context
- Memory Formation Pipeline
- Automation Scheduler
- Source / Event Model
- Skill Resolver
- Context Builder
- Personal State Service
- Tool Policy Layer

例如：

“Attention”不是 LangGraph 官方定义的组件。

它是为了实现“用户聊天时，Agent 能顺带发现当前重要事务”而设计的项目层能力。

==================================================
4. 主 Agent Graph
==================================================

V1 主 Graph 保持尽可能简单。

推荐逻辑：

START
  ↓
restore_runtime
  ↓
build_initial_context
  ↓
Executive Agent
  ↓
Decision
  ├── Respond
  │      ↓
  │     END
  │
  ├── Ask User
  │      ↓
  │   interrupt()
  │      ↓
  │    resume
  │      ↓
  │ Executive Agent
  │
  └── Tool / Specialist
         ↓
     Policy Check
         ↓
       Execute
         ↓
     Tool Result
         ↓
   Executive Agent
         ↓
        loop


关键原则：

1. 不为每一种“思考动作”创建一个固定 LLM 节点。
2. 不把 Personal State 读写做成固定前后置节点。
3. 不把 Memory Formation 做成每次 Agent Run 结束前的同步节点。
4. 不把 Perception 做成所有图片/文件输入的固定前置模型调用。
5. 主 Agent 保持最终回答与全局决策控制权。
6. 专家能力优先作为 Tool；真正需要独立多步推理时才升级成 Subgraph / Specialist Agent。


==================================================
5. LangGraph State 设计
==================================================

LangGraph State 是“当前 Agent Run / Thread 的工作状态”。

它不是：

- Personal State 数据库；
- Long-term Memory 数据库；
- Thing 数据库。

Graph State 应尽量保存原始运行数据，而不是提前拼接好的大 Prompt。


V1 建议结构：

GraphState
├── messages
├── current_input
├── thread_id
├── user_id
├── run_id
├── active_thing_refs
├── source_refs
├── retrieved_memory
├── prefetched_state
├── attention_candidates
├── loaded_skills
├── tool_results
├── pending_actions
├── working_plan
├── interrupt_context
├── execution_results
└── runtime_metadata


说明：

messages
- 当前 Thread 消息。

active_thing_refs
- 当前高概率相关 Thing ID。
- 只保存引用或少量摘要，不复制完整数据库对象。

retrieved_memory
- 本轮 Initial Retrieval 已找到的相关长期记忆。

prefetched_state
- 为第一轮推理预取的少量 Personal State。

attention_candidates
- 当前值得关注的少量事项。

loaded_skills
- 当前任务需要的 Skill / Instructions。

tool_results
- 当前 Agent Run 中 Tool 返回结果。

working_plan
- Agent 在复杂任务中产生的短期计划。
- 不要求所有任务都有 Plan。

pending_actions
- 尚未执行或等待确认的操作。

interrupt_context
- Agent 暂停等待用户时所需数据。


原则：

数据库是真实业务数据源；
Graph State 是 Agent 当前工作的“桌面”。


==================================================
6. restore_runtime
==================================================

restore_runtime 是确定性运行时恢复步骤。

职责：

- 根据 thread_id 加载 LangGraph checkpoint；
- 恢复 messages；
- 恢复 pending tool state；
- 恢复 interrupt；
- 恢复当前 run 所需的 runtime metadata。

它不负责：

- 搜索长期 Memory；
- 读取全部 Personal State；
- 让 LLM 判断用户意图；
- 重新解析文件。


Thread 使用 LangGraph Checkpointer 持久化。

生产环境计划使用 PostgreSQL-backed checkpointer。


Thread 和 Thing 必须完全分离。

例如：

Thread A
Thread B
Thread C

都可以讨论：

Thing = “鸿蒙应用开发者激励计划”

因此不能用 thread_id 表示现实事务 ID。


==================================================
7. build_initial_context
==================================================

build_initial_context 的目标不是“加载所有上下文”。

目标是：

在第一次 Executive Agent inference 前，
用最低成本提供最可能有价值的信息。


输入：

- current_input
- current Thread
- source_refs
- user_id
- possible thing hints


输出可能包含：

Context
├── Recent Thread Context
├── Thread Summary（必要时）
├── Relevant Profile Memory
├── Relevant Semantic Memory
├── Relevant Episodic Memory
├── Optional Relevant Personal State
├── Attention Candidates
├── Relevant Skills
└── Source Metadata


--------------------------------------------------
7.1 Hybrid Context Strategy
--------------------------------------------------

采用：

Relevant Prefetch
+
Agentic Just-in-Time Retrieval


例 1：

用户：

“Demo做完了。”

当前 Thread 显然一直在讨论 Thing A。

可以预取：

Thing A 简要状态
+
相关 tasks

这样 Executive Agent 第一轮就有足够信息，不必：

LLM
→ state.get_thing
→ LLM

增加额外 round trip。


例 2：

用户：

“Python 的 list 和 tuple 有什么区别？”

没有明显事务关联。

build_initial_context 不查询 Personal State。


例 3：

用户：

“之前那个比赛为什么我们决定不用多 Agent？”

可以预检索 Semantic Memory。

如果仍然不足：

Executive Agent
→ memory.search(...)


--------------------------------------------------
7.2 Context Budget
--------------------------------------------------

Context Builder 应限制：

- 每种 Memory 数量；
- Personal State 摘要长度；
- Attention Candidate 数量；
- Tool schema 数量；
- Thread history 长度。


建议初期：

Attention Candidate <= 3

Personal State：
只预取高置信相关 Thing。

Memory：
优先 Top-K relevant memories。

长 Thread：
Recent Messages + Summary。


==================================================
8. Executive Agent
==================================================

Executive Agent 是系统唯一默认用户交互 Owner。

主要职责：

1. 理解用户当前需求；
2. 判断当前事务；
3. 判断现有 Context 是否足够；
4. 决定回答还是行动；
5. 形成必要的短期执行计划；
6. 选择 Tool；
7. 判断是否可以并行；
8. 判断是否调用 Specialist；
9. 综合 Tool / Specialist 结果；
10. 判断结果是否可信；
11. 判断是否更新 Personal State；
12. 判断是否需要追问用户；
13. 控制最终回答；
14. 判断 Attention 是否适合此时出现。


Executive Agent 可以拥有：

Instructions
+
Current Context
+
Tool Registry
+
Relevant Skills


但不直接拥有：

SQL connection
database transaction
filesystem raw access
Push credential
calendar credential

这些必须通过受控 Tool / Service。


==================================================
9. Agent Decision Types
==================================================

从产品和运行角度，Agent 的主要决策可以抽象为：

A. RESPOND

直接回答用户。

B. ASK_USER

信息不足，需要用户输入。

C. CALL_TOOL

调用一个或多个 Tool。

D. DELEGATE

调用 Specialist Agent / Subgraph。

E. CONTINUE

根据 Tool Result 再推理。

F. COMPLETE

任务完成并结束 Run。


不要求 LLM 每轮必须显式输出这些英文枚举。

实现时可以：

- 使用模型原生 Tool Calling；
- 使用 structured output；
- 使用 LangGraph Command / Conditional Routing；

根据具体实现选择。

10. Tool Architecture
==================================================

Tool 是 Executive Agent 与真实环境之间的接口。


建议逻辑分层：

Executive Agent
      ↓
Tool Call
      ↓
Tool Router / Registry
      ↓
Policy Layer
      ↓
Domain Service
      ↓
External API / Database
      ↓
Normalized Tool Result
      ↓
Executive Agent


Tool 不应只是：

@tool
def update_db():
    SQL...


而应通过 Service 层保护业务规则。


例如：

state.update_task_status
        ↓
StatePolicy
        ↓
PersonalStateService
        ↓
validation
version check
idempotency
transaction
        ↓
database
        ↓
StateMutationResult

12. Tool Result
==================================================

所有 Tool 返回统一可机器理解的 Result。

建议：

ToolResult
├── status
├── data
├── error
├── source_refs
├── mutation_refs
├── retryable
└── metadata


status 可表示：

success
partial
failed
requires_confirmation
not_found
conflict


Agent 必须根据真实 Tool Result 回答。

禁止：

Tool 返回 failed
但模型回复“已经帮你完成”。


==================================================
13. Personal State 的读取
==================================================

Personal State Read 使用两条路径。


--------------------------------------------------
13.1 Relevant Prefetch
--------------------------------------------------

如果 build_initial_context 已经高置信识别当前 Thing：

提前读取最少必要字段。

例如：

Thing summary
tasks
deadline
status


--------------------------------------------------
13.2 Agentic Drill-down
--------------------------------------------------

如果第一轮推理后需要更具体的数据：

Executive Agent
→ state.get_thing
→ state.get_history
→ state.get_tasks
→ ...


因此：

Personal State 不是“每轮全部加载”。

也不是“任何时候都必须先 Tool Call”。

而是：

小量相关数据可预取
+
深入信息按需 Tool Retrieval。


==================================================
14. Personal State 的写入
==================================================

Personal State Write 永远发生在 Agent 判断之后。


正确流程：

User Input
    ↓
Context
    ↓
Executive Agent
    ↓
判断这是否是真实状态变化
    ↓
必要时验证 / Search / Ask
    ↓
state.update_*
    ↓
Policy / Service
    ↓
Commit
    ↓
Mutation Result
    ↓
Executive Agent
    ↓
Respond


例：

“Demo做完了。”

高置信：
→ state.update_task(DONE)


例：

“听说截止日期可能改到22号。”

低置信：
→ 不立即修改 deadline
→ search.official / ask
→ 确认
→ state.set_deadline


Personal State 当前状态优先级高于旧 Memory。

如果两者冲突：

Current Personal State
>
Old Long-term Memory

==================================================
16. Long-term Memory 写入
==================================================

常规长期 Memory 不在主 Agent Graph 每轮同步生成。


推荐：

Conversation / State Events
        ↓
Event Queue
        ↓
Debounce / Batch
        ↓
Memory Formation Worker
        ↓
Relevant Existing Memory
        ↓
Memory Manager
        ↓
┌────────────┬─────────────┬─────────────┐
│            │             │             │
Profile   Semantic      Episodic       Ignore
Update    Upsert        Insert
        ↓
Long-term Memory Store


Memory Manager 需要知道：

- 最近 Conversation Events；
- 当前相关 Personal State；
- 已存在相关 Memory；
- 什么信息不应该重复存储。


原则：

当前任务状态不复制成 Memory 的权威事实。

例如：

“报告当前 TODO”

只在 Personal State。

而：

“用户习惯在截止前一天收到提醒”

可以进入 Profile Memory。


明确命令：

“记住这个。”

可以立即触发 Memory Formation / Memory Write。

不必等待批处理。


==================================================
17. Attention Architecture
==================================================

Attention 是 Personal State 的轻量主动性投影。


推荐初期：

不要单独做复杂 Attention DB。

先通过查询 / 规则产生 candidates。


AttentionService:

get_candidates(
    user_id,
    now,
    limit
)


规则可能包括：

deadline < now
→ overdue

deadline = today
→ due_today

deadline soon
→ due_soon

priority = high
→ high_priority

blocked duration > threshold
→ blocked_too_long

important Thing inactive too long
→ inactive_important


返回：

AttentionCandidate
├── thing_id
├── task_id
├── type
├── severity
├── summary
├── due_at
├── last_surfaced_at
├── next_eligible_at
└── acknowledged


build_initial_context 最多加入少量 Candidate。

程序决定：

什么“值得考虑”。

Executive Agent 决定：

此刻“是否应该说”。


==================================================
18. Automation Architecture
==================================================

Automation 与 Agent Thread 分离。


Automation Store
      ↓
Scheduler
      ↓
Trigger
      ↓
System Event
      ↓
Agent Run / Deterministic Action
      ↓
Tool
      ↓
Push / State Update / Result


Automation 类型：

- one-shot
- recurring
- condition watch


Automation 不是 Memory。

未来任务安排应进入 Automation Store。


条件监控示例：

用户：

“官网公布结果后告诉我。”

系统创建：

Condition Watch
      ↓
Scheduler 定期触发
      ↓
search.official
      ↓
condition false
→ end silently

condition true
→ Agent
→ Push


==================================================
19. Push 与 Agent Runtime
==================================================

Push 是 Delivery Channel。

它不是 Agent 自身的一部分。


典型：

Automation Event
      ↓
Agent / Rule
      ↓
Notification Service
      ↓
HarmonyOS Push
      ↓
Device


Push payload 应尽量包含：

- notification type
- title
- summary
- thing_id
- thread_id（可选）
- deep_link target


点击通知：

HarmonyOS App
→ 对应 Thing / Chat / Automation Result


==================================================
20. Source / Ingestion Architecture
==================================================

原始现实输入先保存为 Source。


HarmonyOS Share / Upload
        ↓
FastAPI
        ↓
Source Service
        ↓
Object Storage
+
Source Metadata
        ↓
Create Event


基础处理可包括：

- file type
- mime
- filename
- size
- hash
- timestamps
- basic parser result


不要默认：

File
→ LLM Extractor
→ 自动改 Personal State


正确：

File
→ Source Saved
→ Event
→ Executive Agent
→ 根据用户意图决定是否：
   document.interpret
   image.interpret
   search

==================================================
21. Perception Architecture
==================================================

Perception 是 Tool / Capability。


图片：

image.interpret(source_id)

文档：

document.interpret(source_id)

语音：

audio.interpret(source_id)


内部可以使用：

OCR
Parser
Vision Model
Document Model
Speech-to-Text
Structured Output


但 Executive Agent 不关心底层供应商。


如果未来 document.interpret 变复杂：

read pages
→ parse tables
→ inspect image
→ search
→ verify
→ synthesize

可以把其内部升级为：

Document Specialist Subgraph

但对 Executive Agent 仍表现为一个 Tool。


==================================================
22. Skill Architecture
==================================================

Skill 表示：

“处理某类任务时，应采用什么专业规则和流程知识。”


Skill 不是：

User Memory
Personal State
Tool
Agent


例如：

Competition Skill

可以包含：

- 区分报名截止 / 提交截止；
- 核实规则优先官方来源；
- 常见字段；
- Eligibility；
- Deliverables；
- 推荐 Tool；
- 状态更新原则。


Skill 加载策略：

Current Input
+
Thing Type
+
Task Type
        ↓
Skill Resolver
        ↓
Relevant Skills
        ↓
Context


不要把所有 Skill 每轮全塞进 Prompt。


==================================================
23. 自主规划
==================================================

Executive Agent 可以根据任务复杂度形成 Working Plan。


简单任务：

“Demo完成了。”

无需显式 Plan。


复杂任务：

“把这个比赛完整梳理一下，再检查我现在有什么没做。”

Agent 可以形成：

Plan:
1. 获取当前 Thing State
2. 读取最新通知
3. 查询官网
4. 检索历史决定
5. 综合冲突
6. 给出 Next Actions


Working Plan：

属于 Thread / Run 临时状态。

通常不进入 Long-term Memory。


==================================================
24. 并行执行
==================================================

并行是 Execution Strategy。

不是新的顶层架构。


--------------------------------------------------
24.1 Parallel Tool Calls
--------------------------------------------------

独立的数据读取可以并行：

┌─ state.get_thing
├─ search.official
├─ document.interpret
└─ memory.search
        ↓
      Results
        ↓
 Executive Agent


--------------------------------------------------
24.2 Fan-out / Fan-in
--------------------------------------------------

对于动态子任务：

Executive Agent
→ subtasks = [A, B, C, ...]
→ fan-out
→ workers
→ fan-in
→ synthesis


LangGraph 可通过：

- parallel edges
- reducers
- Send

实现。


需要注意：

并行 branch 不应无控制地同时修改同一 Personal State。

推荐：

并行阶段主要负责：

research / read / analyze

最终业务写入尽量回到：

Executive Agent
→ State Tool
→ Transaction


==================================================
25. Specialist Agent / Subgraph
==================================================

V1 不建立固定多 Agent 组织结构。


默认：

Executive Agent
+
Tools


只有能力满足以下特征时，升级为 Specialist：

1. 自己需要多步推理；
2. 需要多次 Tool Call；
3. 需要独立 Context；
4. 输出可以作为一个清晰结果返回；
5. 复用价值较高。


例：

Research Specialist
Document Specialist
Planning Specialist


调用形式：

Executive Agent
→ Specialist as Tool
→ Specialist internal loop
→ compressed result
→ Executive Agent


默认使用：

per-invocation subgraph persistence

即每次调用保持独立。

只有 Specialist 自己需要跨调用对话记忆时，才考虑 per-thread。


==================================================
26. Human-in-the-loop
==================================================

HITL 使用 LangGraph interrupt / resume。


需要暂停的典型场景：

- 高风险真实操作；
- 无法确定目标 Thing；
- Tool 参数缺少关键字段；
- 用户必须做选择；
- 重要状态冲突；
- 外部动作需要审批。


流程：

Executive Agent
      ↓
Need User Input
      ↓
interrupt(payload)
      ↓
Checkpoint Saved
      ↓
API 返回客户端
      ↓
用户回复
      ↓
Command(resume=...)
      ↓
Graph Resume


用户关闭 App 后：

Run 仍可以停留在 checkpoint。

重新打开后恢复。


==================================================
27. Durable Execution
==================================================

LangGraph Checkpoint 用于：

- Thread short-term state；
- interrupt；
- resume；
- fault recovery；
- run inspection。


生产 V1：

PostgreSQL-backed Checkpointer。


Graph State 不等同于业务数据库。

例如：

Tool 执行：

state.update_task
      ↓
PostgreSQL business tables commit

Graph Checkpoint 保存：

tool result
execution position


两套持久化解决不同问题。


==================================================
28. 幂等与副作用
==================================================

任何真实副作用必须考虑：

Agent Run 可能重试；
Graph 可能恢复；
网络可能重复请求；
客户端可能重复提交。


因此 Tool Mutation 应支持：

idempotency_key


建议：

idempotency_key =
run_id
+
action_id


例如：

calendar.create_event(
    ...,
    idempotency_key
)


如果 Agent 第一次：

事件已创建
↓
结果返回前进程崩溃

恢复后再次执行同一 action：

Tool Service
发现 idempotency_key 已成功
↓
返回之前结果

而不是再创建一条事件。


==================================================
29. 并发写冲突
==================================================

用户可能：

- 两个 Thread 同时修改一个 Thing；
- Automation 与用户同时更新；
- 并行 Agent Run 同时产生状态修改。


Personal State 写入建议支持：

version
或
updated_at optimistic concurrency


流程：

Read Thing version=10
↓
Agent proposes mutation
↓
Update WHERE version=10
↓
成功：
version=11

失败：
CONFLICT
↓
重新读取
↓
Agent Reconcile


不要用：

最后一次写入无条件覆盖。


==================================================
30. Error Handling
==================================================

错误分类：

A. Transient Error

例如网络 timeout。

处理：

retry policy。


B. LLM-Recoverable Error

例如 Tool 参数校验失败。

处理：

把错误作为 Tool Result 返回 Agent
→ Agent 修正参数。


C. User-Fixable Error

例如：

“你说的是哪个 Demo？”

处理：

interrupt / Ask User。


D. Permanent External Error

例如文件格式不支持。

明确告诉用户。


E. Unexpected Internal Error

记录 Trace / Error ID
停止当前异常路径
不伪装成功。

32. Thread / Run / Event
==================================================

需要明确三个概念。


Thread

用户对话上下文容器。

可以持续多个 Run。


Run

一次 Agent 执行实例。

可能由：

- 用户消息；
- Automation；
- System Event

触发。


Event

现实世界或系统发生的一件事情。

例如：

- 用户上传 Source；
- Automation 到期；
- 用户发送消息；
- State 变化；
- Push 点击；
- 外部 Tool 返回。


关系：

Thread
  └── Run 1
  └── Run 2
  └── Run 3

System Event
  └── Run X（可以没有用户主动打开 App）

“老师刚说比赛可能延期到22号，你查一下，顺便看看我还有什么没完成。”


① API

收到 user message
↓
create Run


② restore_runtime

加载 thread checkpoint。


③ build_initial_context

Thread：
正在讨论比赛 A

Prefetch Personal State：

Thing A
deadline = 9/19
tasks:
Demo = DONE
报告 = TODO
视频 = TODO

Memory：
历史规则/决定

Attention：
报告即将截止


④ Executive Agent

判断：

- “可能延期”不确定；
- 需要官方验证；
- “还有什么没完成”需要当前 state；
- 两项读取可以并行。


⑤ Parallel Execution

search.official(deadline change)
+
state.get_tasks(Thing A)


⑥ Result

Official：
截止变更确认 = 9/22

State：
报告 TODO
视频 TODO


⑦ Executive Agent

决定：

需要更新 deadline。


⑧ State Tool

state.set_deadline(
Thing A,
9/22,
source=official_source
)


⑨ Tool Result

success
mutation_id = ...

回复：

- 官方已确认延期；
- 截止已更新；
- 当前仍有报告、视频未完成；

⑪ Background

Personal State 没有在用户输入后自动更新。

42. 架构验收 Case
==================================================

A01
普通知识问题不加载全部 Personal State。

A02
明显关联当前 Thing 时允许 lightweight prefetch。

A03
第一轮 Context 不足时 Agent 可以 state.get_* 深挖。

A04
Personal State Write 必须发生在 Agent 判断之后。

A05
不确定外部事实不能直接覆盖权威状态。

A06
Tool failed 时 Agent 不得声称成功。

A07
两个独立 Tool 可以并行。

A08
并行结果可以 fan-in 给 Executive Agent。

A09
复杂子任务可以使用 Specialist Subgraph。

A10
Specialist 默认不拥有最终用户回复控制权。

A11
用户询问时可 interrupt，并在之后 resume。

A12
App 退出后 interrupted run 不丢失。

A13
Thread 与 Thing 相互独立。

A14
新 Thread 可以通过 Personal State / Long-term Memory 恢复相关上下文。

A15
长期 Memory 不复制当前可变任务状态作为权威来源。

A16
Memory Formation 不阻塞每轮正常回复。

A17
Automation 可以在没有用户在线时触发新的 Run。

A18
Attention Candidate 由规则筛选，是否提醒由 Agent 决定。

A19
Perception 是按需 Tool，不是所有文件必经 LLM 节点。

A20
Side-effect Tool 必须考虑幂等。

A21
并行 Tool 不应直接竞争修改同一业务字段。

A22
State 并发修改冲突可以检测，而非静默覆盖。

A23
长 Thread 可以进行 compaction / summary。

A24
Tool、Agent、Background Worker 均可追踪。

A25
模型供应商可替换，不影响业务核心架构。

45. 最终架构定义
==================================================

老实人的 Agent 系统定义为：

一个由 LangGraph 承载 durable runtime 的单主 Agent 系统。

Executive Agent 是用户交互与全局决策中心。

每一次 Run：

先恢复 Thread Runtime，
再构造最小高价值 Initial Context，
随后由 Executive Agent 自主判断：

- 是否回答；
- 是否追问；
- 是否读取更多 Personal State；
- 是否检索 Memory；
- 是否理解 Source；
- 是否搜索外部信息；
- 是否执行真实 Tool；
- 是否并行；
- 是否委派 Specialist；
- 是否更新当前现实状态；
- 是否继续推理。

Personal State 是现实事务当前状态的权威存储，
不属于 LangGraph State。

Long-term Memory 保存跨对话长期事实、偏好和经验，
通过检索进入 Context，
并由后台 Memory Formation Pipeline 持续形成。

Attention 负责用户在线时的机会式主动提醒。

Automation 负责用户不在线时的未来触发。

Perception、Search、Calendar、Notification 等均通过 Tool / Capability 暴露。

复杂能力只有在确实需要独立多步自主执行时，
才升级为 Specialist Agent / LangGraph Subgraph。

最终形成：

Past
Long-term Memory

Now
Personal State

What matters now
Attention

Reasoning and control
Executive Agent

Action
Tools

Future
Automation


这五部分共同组成老实人的核心 Agent 系统。

46. 官方设计依据（截至 2026-08）
==================================================

1. LangGraph - Thinking in LangGraph
https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph

关键依据：
- State 作为步骤间共享运行状态；
- State 保留 raw data，在需要时格式化 Prompt；
- Node 可包含 LLM、Data、Action、User Input；
- Human input / interrupt 是一等能力。


2. LangGraph - Persistence
https://docs.langchain.com/oss/python/langgraph/persistence

关键依据：
- Checkpoint 按 Thread 持久化；
- 支持 HITL、conversation memory、fault tolerance；
- checkpoint 可恢复执行；
- 并行 superstep 中成功节点的 pending writes 可持久保存。


3. LangGraph - Interrupts
https://docs.langchain.com/oss/python/langgraph/interrupts

关键依据：
- interrupt 可以暂停 Graph；
- Checkpointer 保存当前状态；
- 之后使用 Command resume；
- side effect 需要考虑 idempotency。


4. LangGraph - Graph API
https://docs.langchain.com/oss/python/langgraph/use-graph-api

关键依据：
- 原生 parallel execution；
- fan-out / fan-in；
- reducers；
- Send 动态 map-reduce。


5. LangGraph - Subgraphs
https://docs.langchain.com/oss/python/langgraph/use-subgraphs

关键依据：
- Specialist / Subgraph 可拥有独立 state；
- per-invocation persistence 适合大多数独立 multi-agent tool-style 调用；
- 只有需要跨调用记忆时才使用 per-thread。


6. Anthropic - Effective context engineering for AI agents
https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

关键依据：
- Context 是有限资源；
- 应优先保留高价值 Context；
- Agent 可以通过 Tool just-in-time 获取信息；
- 实际系统可使用预取 + 按需检索的混合策略。


7. OpenAI Agents SDK - Agents / Tools
https://openai.github.io/openai-agents-python/
https://openai.github.io/openai-agents-python/tools/

关键依据：
- Agent = model + instructions + tools；
- 内置 Agent loop；
- Agent 可以作为另一个 Agent 的 Tool；
- Manager-style orchestration 可以保持主 Agent 控制。
